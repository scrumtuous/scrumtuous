Big picture

The Two Hardest SOLID Principles to Spot

S, O, and L often look obviously wrong in one file. I and D often feel like normal friction until you learn to recognize the pattern.

🧩 ISP smell "Why am I implementing methods I never use?"
🔌 DIP smell "Why can I only test this class by writing to the real console, file, or service?"
✂️ ISP fix Split a broad contract into focused capabilities.
🔄 DIP fix Supply an abstraction from outside instead of building a concrete dependency inside.
I: The problem

A Fat Interface Forces Irrelevant Methods on Classes

For MadShapes, imagine bundling every output style into one giant interface.

public interface ShapeOutputBad {
    String toConsole(Shape shape);
    String toCsv(Shape shape);
    String toSvg(Shape shape);
}

public class CsvShapeExporterBad
        implements ShapeOutputBad {

    @Override
    public String toCsv(Shape shape) {
        return shape.getLabel() + "," +
               shape.calcArea();
    }

    @Override
    public String toConsole(Shape shape) {
        throw new UnsupportedOperationException();
    }

    @Override
    public String toSvg(Shape shape) {
        throw new UnsupportedOperationException();
    }
}
The smell
The type promises capabilities the class cannot actually provide. Callers can legally call toSvg(), yet the method explodes at runtime.
Quiz hint: being forced to implement methods you do not need is a classic Interface Segregation violation.

🌸 Quick check

Why is throwing UnsupportedOperationException from an interface method a warning sign here?

The interface says the class can perform the operation, but the implementation cannot.
That means the contract is broader than the class actually needs or supports.
I: The principle

Interface Segregation: Depend Only on What You Need

Split a large contract into smaller capabilities, then implement only the ones that fit.

CsvExportable

One capability: export a shape as CSV.

String toCsv(Shape shape);

ConsolePrintable

One capability: render a readable console representation.

String toConsole(Shape shape);

SvgRenderable

One capability: produce SVG output.

String toSvg(Shape shape); 
public interface CsvExportable {
    String toCsv(Shape shape);
}

public class CsvShapeExporter
        implements CsvExportable {

    @Override
    public String toCsv(Shape shape) {
        return shape.getLabel() + "," +
               shape.calcArea();
    }
}
Payoff
There is no unused method left to stub. The compiler removes the invalid capability from the type entirely.
Direct exam connection: if a CSV-only class implements ConsoleReportable "for future flexibility", that adds unnecessary coupling and violates Interface Segregation.
ROFLGator contract advice If the class only needs CSV, give it CSV. Do not hand it a buffet of unrelated methods and then complain about the leftovers.
D: The problem

High-Level Code Wired Directly to a Concrete Detail

Now imagine the MadShapes experiment always constructs a console writer internally.

public class BadExperimentRunner {

    private final ConsoleResultWriter writer =
        new ConsoleResultWriter();

    public boolean run(
            Shape first,
            Shape second) {

        boolean same =
            first.calcArea() == second.calcArea();

        writer.write(
            same ? "SAME" : "DIFFERENT"
        );

        return same;
    }
}
The friction
The high-level class decides both what to do and exactly how output happens. Testing it means touching the real console. Switching to a file or in-memory writer means editing the class.
Quiz clue: directly constructing new ConsoleReportWriter() inside OrderExecutor is the problem. The high-level policy is coupled to one low-level detail.
D: The principle

Dependency Inversion: Both Sides Depend on an Abstraction

public interface ResultWriter {
    void write(String result);
}

public class ExperimentRunner {
    private final ResultWriter writer;

    public ExperimentRunner(
            ResultWriter writer) {
        this.writer = writer;
    }

    public boolean run(
            Shape first,
            Shape second) {

        boolean same =
            first.calcArea() == second.calcArea();

        writer.write(
            same ? "SAME" : "DIFFERENT"
        );

        return same;
    }
}

Real use

new ExperimentRunner(
    new ConsoleResultWriter()
);

Unit test

new ExperimentRunner(
    new InMemoryResultWriter()
);
The important distinction
Constructor injection is the mechanism. Dependency Inversion is the design principle. The high-level class no longer reaches down to choose a concrete writer.
Direct exam connection: constructor injection of ReportWriter enables an in-memory test writer and demonstrates Dependency Inversion because the high-level class depends on the abstraction.

🔌 Quick check

What is the strongest reason to accept ResultWriter in the constructor instead of constructing ConsoleResultWriter internally?

The high-level class depends on an abstraction instead of one concrete output mechanism.
That makes the class easier to test and lets different writers be supplied without changing the class.
Why the name feels weird

"Dependency Inversion" Is Bigger Than "Dependency Injection"

Without inversion

ExperimentRunner reaches downward and creates ConsoleResultWriter.

The policy knows the concrete detail.

With inversion

ExperimentRunner and ConsoleResultWriter both rely on ResultWriter.

The detail satisfies the abstraction expected by the policy.

Remember the phrase: high-level policy should not depend directly on low-level detail. Both depend on an abstraction.
Jimbo James wiring strategy Jimbo James of the Columbian cartel proposed hard-coding every concrete dependency because "we know what we want today." The testing team has requested changes.
Testability payoff

Why an In-Memory Writer Matters

An in-memory implementation is not fake architecture. It demonstrates that the high-level class is decoupled from side effects.

public class InMemoryResultWriter
        implements ResultWriter {

    private String lastResult;

    @Override
    public void write(String result) {
        lastResult = result;
    }

    public String getLastResult() {
        return lastResult;
    }
}

Without DIP

Unit tests may have to capture console output, touch a file, or hit a real service.

With DIP

The test supplies a tiny in-memory collaborator and inspects what was written.

Coming soon: TDD, JUnit, and Mockito all benefit from the same design move. Testability is often a side effect of good dependency boundaries.
