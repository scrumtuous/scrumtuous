Read the Requirement Before Writing a Test

Mission requirement 3:
  • Before an order can be processed, it must be validated.
  • The quantity must be positive.
  • The price must be positive.
  • A sell order cannot reduce a holding below zero.
  • A buy order cannot exceed the risk limit.
Why this matters
The requirement gives us candidate test cases. Each clause can become one or more cycles.
Mission invariant: an invalid order should be rejected before execution. That means portfolio or holding state must remain unchanged on the rejected path.
Cycle 1

The First Test Might Not Even Compile

RED

Simplest valid buy

@Test
void acceptsAValidBuyOrder() {
    var request =
        new OrderRequest(10, 100, true);

    var result = validator.validate(
        request,
        0,
        0,
        5000
    );

    assertTrue(result.isValid());
}

The test may fail before it even runs because OrderRequest or ValidationResult does not exist yet.

GREEN

Create the smallest types that satisfy the behavior

Do not build the whole validator in one jump. Make the test compile, then make the one demonstrated behavior pass.

TDD allows compile failures: red can mean a failing assertion, missing method, or missing class. The point is that the new behavior is not yet supported.
Design emerges

The Requirement Forces a ValidationResult

A boolean could answer "valid or invalid", but the mission also says a rejected order needs a reason. That makes a plain boolean too weak.

Too little information

boolean validate(OrderRequest request)

A caller learns only yes or no.

Requirement-shaped result

public class ValidationResult {
    public static ValidationResult valid()

    public static ValidationResult invalid(
        String reason)

    public boolean isValid()

    public String getReason()
}

Now rejection can carry the reason required by the workflow.

The lesson
The test surfaced a design need that the implementation must support. TDD can shape APIs and object boundaries, not just method internals.
Important reasoning: the result object exists because the requirement needs more than a yes/no answer. That is a design decision driven by behavior.
ROFLGator architecture note Do not invent a pattern because it has a fancy name. Let the requirement show when the richer type is needed.
Traceability

Each Cycle Maps Back to One Clause

Cycle Requirement clause Test pressure
1 A valid order can proceed Create the minimum request, validator, and result API.
2 Quantity must be positive Reject quantity of zero or less with a reason.
3 Price must be positive Add price validation only when this test arrives.
4 Sell cannot reduce holding below zero Current holding quantity becomes relevant.
5 Buy cannot exceed risk limit Portfolio value and risk limit become relevant.
Subtle TDD point
Some parameters can exist before a test needs them. The holding quantity may be present in Cycle 1, but it should not gain behavior until Cycle 4 actually demands it.
The lab

HoldingUpdater Is the Complementary Half

OrderValidator decides whether an order should proceed. HoldingUpdater applies an order that has already passed validation.

Green: the minimum implementation can handle buying only.

2

Green: now isBuy must force a branch.

Green: add a guard clause.

Holding 100, sell 200, expect exception.

Green: may already pass because Holding.adjust() protects its invariant.

Cycle examples

Let Each Test Earn the Next Implementation Change

Cycle 1 RED
@Test
void buyIncreasesHoldingQuantity() {
    Holding holding = new Holding(100);

    updater.applyOrder(
        holding,
        true,
        10
    );

    assertEquals(
        110,
        holding.getQuantity()
    );
}
Cycle 1 GREEN
public void applyOrder(
        Holding holding,
        boolean isBuy,
        double quantity) {

    holding.adjust(quantity);
}

This does not handle selling yet. That is fine. No sell test has earned that branch yet.

Cycle 2 RED
@Test
void sellDecreasesHoldingQuantity() {
    Holding holding = new Holding(100);

    updater.applyOrder(
        holding,
        false,
        10
    );

    assertEquals(
        90,
        holding.getQuantity()
    );
}
Cycle 2 GREEN
public void applyOrder(
        Holding holding,
        boolean isBuy,
        double quantity) {

    if (isBuy) {
        holding.adjust(quantity);
        return;
    }

    holding.adjust(-quantity);
}
Strict TDD reminder: the first implementation may look incomplete because it is incomplete. The missing behavior should arrive through the next failing test, not prediction.
Delegation

An Over-Large Sell May Already Be Green

@Test
void sellingMoreThanTheHoldingThrows() {
    Holding holding = new Holding(100);

    assertThrows(
        IllegalArgumentException.class,
        () -> updater.applyOrder(
            holding,
            false,
            200
        )
    );
}
What if it passes immediately?
That test still matters. It confirms that HoldingUpdater delegates to Holding.adjust(), and that the Holding still protects its own non-negative invariant.
Evidence matters: a test does not need to force new code to be useful. It can confirm that an existing collaborator already enforces the required boundary.
Apparent duplication

Two Classes Checking a Similar Rule Can Still Be Correct

OrderValidator

Purpose: decide whether the order should proceed before execution.

It compares a sell quantity to a plain current holding quantity.

Holding

Purpose: protect its own state during mutation.

adjust() refuses any change that would make quantity negative.

Clean Code nuance
Similar logic is not automatically duplicated responsibility. Ask whether the checks protect different boundaries at different points in the workflow.

🧠 Design question

Is it necessarily wrong that both validation and Holding can reject an over-large sell?

No.

OrderValidator protects the workflow before execution.
Holding protects its own invariant during mutation.

The rules look similar, but the classes are guarding different boundaries for different reasons.
Jimbo James duplication audit Jimbo James of the Columbian cartel tried to remove the Holding invariant because validation already checked it. The domain object has formally objected.
JUnit organization

Refactor the Test Suite Around Behavior

After the behavior is green, organize the test class using the JUnit techniques from Module 11.

@Nested
@DisplayName("when buying")
class WhenBuying {

    @Test
    @DisplayName("a valid quantity increases the holding")
    void validBuyIncreasesHolding() {
        // ...
    }

    @Test
    @DisplayName("a non-positive quantity is rejected")
    void invalidBuyQuantityThrows() {
        // ...
    }
}

@Nested
@DisplayName("when selling")
class WhenSelling {

    @Test
    @DisplayName("a valid quantity decreases the holding")
    void validSellDecreasesHolding() {
        // ...
    }

    @Test
    @DisplayName("selling more than the holding is rejected")
    void oversizedSellThrows() {
        // ...
    }
}
when buying
✓ a valid quantity increases the holding
✓ a non-positive quantity is rejected
when selling
✓ a valid quantity decreases the holding
✓ selling more than the holding is rejected
JUnit carries forward: @Nested and @DisplayName are not decoration. They make the suite mirror the business behavior and produce readable test reports.

🎓 Final challenge

Cycle 4's over-large-sell test passes immediately because Holding.adjust() already throws. Did the cycle fail to teach anything?

No.

The passing test is evidence that HoldingUpdater delegates to Holding correctly and that Holding still protects its own non-negative invariant.

The test documents and protects that collaboration even though no new implementation was needed.
