Concept 1

Why Review a Design Before Code Exists?

A flaw in a class diagram costs a conversation. The same flaw after implementation can cost a rewrite, new tests, migration work, and more review.

Catch it now

"ShapeManager is doing too much. Split comparison and result recording."

Cost: update a diagram and a worksheet.

Catch it later

"ShapeManager is doing too much. Split comparison and result recording."

Cost: refactor classes, tests, callers, and possibly persistence.

Mindset
Peer review is a second independent reading of the requirements. It is not a contest to find the most mistakes.
Concept 2

What a Useful Review Comment Looks Like

🚫 Vague
"This class does too much."

The concern may be valid, but the author still has to guess what to do next.

✅ Actionable
"ExperimentManager calculates areas, compares shapes, records student responses, and renders results. Consider moving comparison into ShapeComparator and recording into ResultRecorder."

The comment names the problem and gives a useful direction.

Quiz hint: a strong review comment is specific and constructive. It should be detailed enough that the author can act without asking what you meant.

🌸 Rewrite the comment

Improve this: "Your UML relationships are wrong."

"Experiment to Shape is shown as composition, but Shape objects still make sense outside one Experiment. Consider aggregation instead, because deleting the Experiment should not imply deleting the Shape."
Concept 3

The Six-Area Review Checklist

🎯 Responsibility & cohesion Is one class doing noticeably more than the others?
🛡️ Encapsulation Are fields private, or is internal data exposed directly?
♻️ Reuse existing work Does the design duplicate behavior already owned elsewhere?
🔗 Relationships Are association, aggregation, composition, inheritance, and interfaces used correctly?
🎬 Behavior Does the sequence diagram match the class diagram and requirements?
🧭 Traceability Can each class and responsibility be traced back to an actual requirement?

Reviewing a Flawed MadShapes Design

🚨 Flawed class: ShapeExperimentManager
ShapeExperimentManager
Public fields
+ shapeA
+ shapeB
+ studentResponse
Methods
+ calculateCircleArea()
+ calculateRectangleArea()
+ compareAreas()
+ recordResponse()
+ saveToDatabase()
+ sendEmail()
🎯 Responsibility Too many jobs are concentrated in one class. Comparison, recording, persistence, and communication are separate concerns.
🛡️ Encapsulation Public fields allow outside code to modify state without the class controlling it.
♻️ Reuse Shape-specific area calculations duplicate behavior that belongs on Circle, Rectangle, Triangle, and other shapes.
🧭 Traceability sendEmail() does not appear in the current MadShapes requirements. It looks like scope creep.

Review decision

These issues affect the structure of the design, not just naming or formatting.

Exam connection: an explicit approve-or-change-request decision with one sentence of reasoning is part of the expected peer-review practice.
ROFLGator review note "It coordinates everything" is not automatically a defense of a giant manager class. Coordination can still be split into focused collaborators.

Concept 4

Receiving Feedback Without Shutting the Conversation Down

🚫 Defensive

"It's fine. The ExperimentManager is supposed to do all of that."

This closes the discussion without addressing the concern.

✅ Constructive

"I put comparison there because it coordinates the trial, but I see the concern. Moving the area comparison into ShapeComparator would keep the manager focused. Does that address it?"

You can disagree or revise, but explain your reasoning.

Important nuance: you do not have to accept every review comment. A reasoned reply is fine. Dismissing the comment without explaining the design choice is not.

💬 Response practice

Your reviewer says: "Judgement should be its own class." You disagree because the current iteration only stores SAME or DIFFERENT. Write a short, non-defensive reply.

I kept Judgement as a simple value because the current requirements only need SAME or DIFFERENT. If we later add response time or confidence, I agree that a separate class may become useful. Does that address the concern?

🎓 Final review challenge

You find three issues: public fields, duplicated area calculation inside ShapeManager, and a sendEmail() method that does not appear in the requirements. Write one actionable comment and choose Approve or Request Changes.

Comment:
"ShapeManager exposes mutable fields and duplicates area logic already owned by the shape classes. Make the fields private and delegate area calculation back to Shape. Also remove sendEmail() unless a requirement can justify it."

Decision:
Request Changes

Reason:
The current design duplicates responsibilities and includes behavior that is not traceable to the requirements, so implementing it now would likely create rework later.
Module summary

Good peer review turns "I don't like it" into "here is what I saw, why it matters, and what to consider next."

You learned a six-area review checklist, practiced actionable comments, made approve or request-changes decisions, and practiced receiving feedback without shutting the conversation down.
