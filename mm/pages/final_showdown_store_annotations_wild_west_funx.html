The Final Showdown at Gunsmoke Gulch

This capstone challenge turns you loose in a half-finished Spring Boot store app. The data loader runs, the H2 database is waiting, Swagger is pointing at a broken API, and a pile of missing annotations is standing in the street like a gang of outlaws. Your job is to put the codebase back together and make the API ride.

Wild West theme JPA mappings REST endpoints Swagger + H2 CommandLineRunner
Run command: mvn spring-boot:run
This launches the app, triggers the CommandLineRunner, processes the CSV-style purchase rows, and loads the H2 database so you can inspect the data.
Jump to the challenge Starter code on GitHub

What makes this showdown fun?

You are not starting from nothing. You already have a model, a repository, a service, a data loader, and a mostly sketched REST controller. That means the challenge is about reading code, placing the right annotations, testing assumptions, and making the pieces work together.

  • Step 1. Add the missing annotations to the domain classes, service class, application class, and REST controller.
  • Step 2. Run the app with mvn spring-boot:run.
  • Step 3. Verify that the app starts and that the CommandLineRunner loads the CSV data through StoreService.
  • Step 4. Open Swagger UI at http://localhost:8080/swagger-ui/index.html. Only the customer-by-name endpoint works correctly at first.
  • Step 5. Open H2 Console at http://localhost:8080/h2-console/ and confirm the data exists.
  • Step 6. Update the broken REST API, but only use CustomerRepository. Navigate the object graph from customers to purchases to products.
  • Step 7. If JSON recursion gets messy, temporarily simplify or remove some bidirectional mappings for the API phase, then re-add them later.
  • Step 8. Add create methods, such as creating a customer, address, or product, after the read-only API works.

Rules of engagement

Use only CustomerRepository for data access in the REST API.
Use object navigation for related data, not a new repository for every table.
Confirm database success first, then fix API behavior.
Treat Swagger and H2 as proof that your boot camp outpost is alive.
Only /customers/by-name is working at the start.
After the GET endpoints work, add POST endpoints as a stretch goal.
Quiz hint: Be ready to explain why @Entity, @Id, @GeneratedValue, @Embedded, @OneToMany, @ManyToOne, @Service, @RestController, and @RequestMapping matter. Also be ready to explain what CommandLineRunner does during application startup.

Canvas UML: the object model at high noon

This is the model you will be navigating through CustomerRepository. Customer owns purchases. Purchase owns products. Customer also embeds Address. The API challenge gets easier as soon as you see this shape clearly.

How to think through the API using one repository

  • Find customers with customerRepository.findAll() or findByName().
  • Filter in memory when the endpoint is asking about a city or a customer id.
  • From each Customer, navigate to purchases.
  • From each Purchase, navigate to products.
  • Refunds are represented by the state of the remaining product and purchase data after refunds are processed. Your mock data helper shows one possible output shape.
  • Use DTO-like maps or custom response objects if you want to avoid returning the raw graph directly.
Serialization caution: Bidirectional JPA mappings can produce recursion or noisy JSON. It is completely fair to simplify the graph at the API boundary first, then tighten the model later.

Challenge steps, detailed

  1. Fix the bootstrapping. Add @SpringBootApplication to App so Spring Boot can start.
  2. Fix the model. Mark the entities and relationships so JPA can create the schema.
  3. Fix the service layer. Add @Service and @Transactional so the data-loading flow is managed correctly.
  4. Run the app. Use mvn spring-boot:run.
  5. Inspect the evidence. Use the H2 console and confirm customers, purchases, and products exist.
  6. Repair the REST controller. Add the controller annotations and fill in the null-returning methods.
  7. Test through Swagger. Use the UI to verify each endpoint.
  8. Add creates. Once reads work, add methods to create a customer, create an address, create a purchase, or add a product.

Suggested GET mapping layout

@RestController
@RequestMapping("/api")
public class StoreRestController {

  @GetMapping
  public Map<String,String> apiIndex() { ... }

  @GetMapping("/customers")
  public List<Map<String,Object>> customers(...) { ... }

  @GetMapping("/customers/by-name")
  public Map<String,Object> customerByName(...) { ... }

  @GetMapping("/customers/{customerId:\d+}")
  public Map<String,Object> customer(...) { ... }

  @GetMapping("/customers/{customerId:\d+}/purchases")
  @GetMapping("/customers/{customerId:\d+}/refunds")
  @GetMapping("/cities")
  @GetMapping("/cities/{city}/purchases")
  @GetMapping("/cities/{city}/refunds")
  @GetMapping("/products")
  @GetMapping("/products/{productId}")
  @GetMapping("/purchases")
  @GetMapping("/purchases/{purchaseId}")
  @GetMapping("/refunds")
  @GetMapping("/refunds/{refundId}")
  @GetMapping("/summary")
}

Stretch goals after the shootout

  • Add POST methods to create a Customer.
  • Add a method to attach an Address to a customer.
  • Add a method to create a Purchase for a customer.
  • Add a method to create a Product under a purchase.
  • Return cleaner response DTOs instead of raw maps.
  • Reintroduce any bidirectional mappings or serialization helpers you removed while debugging.

Victory conditions

The app starts with mvn spring-boot:run.
The H2 console shows imported data.
Swagger UI loads and routes are visible.
The broken GET endpoints now return real data.
You can explain how the object graph is traversed from Customer to Product.
You have at least one POST or create-style endpoint added.

Boot the app. Check the database. Fix the annotations. Make the API tell the truth. Use one repository, trust the object model, and turn this outlaw codebase into a well-behaved Spring Boot town.
