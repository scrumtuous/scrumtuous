02 / A fresh layer
Two awaits, two different jobs
The first await waits for the fetch promise to fulfill with a Response, once response headers are available. The second await reads and parses the body. A Response is not already your JSON object.
const response = await fetch(url);
const data = await response.json();

Console output
Why did the menu show undefined?
Run the broken version, click the button, and inspect the output. Restore await and test again.
Reveal solution and reasoning
Without await, data holds the promise returned by json(), not the parsed object. data.pancakes is undefined. Await gets the fulfilled object. The event callback must itself be async to use await in it.
await pauses this async function, not the whole browser. The runtime handles completion; promise reactions are queued so JavaScript can resume when the call stack is free. Fetch starts when called, whether or not you await its returned promise.
03 / A fresh layer
POST: package the order correctly
A login request supplies a URL, POST method, JSON content type, and a serialized body. JSON.stringify converts the JavaScript object to JSON text. The server reads that text and parses it.
const response = await fetch("http://localhost:3000/auth/login", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ username, password }),
});
Inspect your request without sending itEdit all three layers
Request builder only: it sends no network request
Console output
Remove the serialization
Remove JSON.stringify around the body object. Inspect body type. Why is a plain object not the JSON request the server expects?
Reveal solution and reasoning
The object is not JSON text. For this JSON API, explicitly serialize it. Other request formats have other body types, such as FormData or URLSearchParams, but they are not interchangeable with a JSON contract.
04 / A fresh layer
HTTP failure is still a response
A 401 or 500 does not by itself reject the fetch promise. You received a Response, but its status is unsuccessful. response.ok is true for 200–299. Check it before announcing success.
QUIZ ALERTThe supplied multi-answer question distinguishes HTTP errors from fetch rejection. Check response.ok for unsuccessful HTTP statuses. Use catch for rejected promises and other exceptions in the try block.

try {
  const response = await fetch(url, options);
  if (!response.ok) { /* report HTTP failure */ return; }
  const data = await response.json();
  /* report success */
} catch (error) {
  /* report request or processing failure */
} finally {
  submitBtn.disabled = false;
}
06 / A fresh layer
CORS: two docks, different origins
An origin is the scheme, host, and port. http://localhost:8000 and http://localhost:3000 differ by port, so the browser’s cross-origin rules apply. A JSON POST typically triggers an OPTIONS preflight to check permission before sending the actual POST.
Compare the originsEdit all three layers
Origin comparison only; it sends no request and does not simulate server headers
Console output
Change the API’s port to 8000, then change http to https. Predict before you click. The actual CORS fix belongs in the authentication service:
const app = await NestFactory.create(AppModule);
app.enableCors({ origin: "http://localhost:8000" });
The server must allow the needed method and headers too; the supplied NestJS setup handles this through enableCors. Putting Access-Control-Allow-Origin into your request headers does not grant permission. mode: "no-cors" does not give you readable cross-origin JSON; it produces an opaque response where applicable.
Some cross-origin requests may be sent even when the browser later blocks script access to the response; others are stopped at preflight. CORS is not authentication. It is enforced by the browser, which is why a working curl request does not prove your browser setup works.

  1. Mark the submit callback async and call preventDefault first.
  2. Await fetch with POST, JSON headers, and a serialized username/password body.
  3. Check response.ok and show the server error body on failure.
  4. Read a successful body and display only the token’s beginning.
  5. Wrap request and body processing in try/catch/finally and re-enable submit on every path.
Reveal real API JavaScript solution
const AUTH_URL = "http://localhost:3000/auth/login";
const form = document.getElementById("login-form");
const usernameInput = document.getElementById("username");
const passwordInput = document.getElementById("password");
const submitBtn = form.querySelector("button[type=submit]");
const message = document.getElementById("message");
function showMessage(text, kind) {
  message.textContent = text;
  message.className = kind;
}
form.addEventListener("submit", async (event) => {
  event.preventDefault();
  if (submitBtn.disabled) return;
  submitBtn.disabled = true;
  showMessage("Logging in...", "");
  let stage = "request";
  try {
    const response = await fetch(AUTH_URL, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        username: usernameInput.value,
        password: passwordInput.value,
      }),
    });
    stage = "response body";
    if (!response.ok) {
      const body = await response.json();
      showMessage(`Login failed: ${body.message ?? response.status}`, "error");
      return;
    }
    const data = await response.json();
    if (typeof data.accessToken !== "string") {
      throw new Error("The response did not contain an accessToken string.");
    }
    showMessage(`Logged in. Token starts: ${data.accessToken.slice(0, 20)}...`, "success");
  } catch (error) {
    console.error(`Failure during ${stage}:`, error);
    showMessage(`Could not complete ${stage}: ${error.message}`, "error");
  } finally {
    submitBtn.disabled = false;
  }
});

What belongs in front-end source?
Anyone can inspect AUTH_URL. Should you move the service URL, database password, and JWT signing secret into the page together?
Reveal solution and reasoning
The API URL is not a secret. Database passwords and JWT signing secrets belong on the server. Do not embed them in shipped JavaScript. A token prefix shown in this classroom lab is not permission to log full tokens in a production app.
