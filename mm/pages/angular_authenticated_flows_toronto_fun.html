02 / A fresh layer

TokenStore: signals and the limits of token presence

import { Injectable, computed, signal } from '@angular/core';
@Injectable({ providedIn: 'root' })
export class TokenStore {
  private readonly token = signal<string | null>(null);
  private readonly username = signal<string | null>(null);
  readonly isAuthenticated = computed(() => this.token() !== null);
  readonly currentUsername = this.username.asReadonly();
  setToken(token: string, username: string): void {
    if (!token.trim()) throw new Error('Empty access token');
    this.token.set(token);
    this.username.set(username);
  }
  getToken(): string | null { return this.token(); }
  clear(): void { this.token.set(null); this.username.set(null); }
}

providedIn: 'root' gives these pieces the same service instance in the application’s root injector. Private writable signals protect the update boundary. A readonly username view supports the shell, while getToken supplies the interceptor. clear changes both values on logout.

The computed isAuthenticated means a token has been stored. It does not verify a JWT signature, expiry, issuer, audience or permissions. A stale or malformed token can still be present. The server must validate every protected request. A frontend expiry check can improve navigation feedback, but decoding a JWT payload is not verifying its signature.

This module stores nothing in localStorage or cookies. Refreshing destroys the application heap and loses the login state. A different tab has its own app instance. Logging out clears this local copy; it does not automatically revoke a JWT already issued by the server.

03 / A fresh layer

Build the login API with an explicit response contract

import { Injectable, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { map } from 'rxjs';
import { AUTH_URL } from './api-urls';
export interface LoginResponse { accessToken: string; }
@Injectable({ providedIn: 'root' })
export class AuthApi {
  private readonly http = inject(HttpClient);
  login(username: string, password: string) {
    // Matches the supplied Node auth API's JSON contract.
    return this.http.post<unknown>(AUTH_URL, { username, password }).pipe(
      map(body => {
        if (typeof body !== 'object' || body === null
          || !('accessToken' in body) || typeof body.accessToken !== 'string'
          || !body.accessToken.trim()) {
          throw new Error('Login response did not contain an access token');
        }
        return { accessToken: body.accessToken } satisfies LoginResponse;
      }),
    );
  }
}

The supplied Node auth API accepts JSON username/password and returns an object with accessToken. That is the contract this code implements. A separate Spring auth tutorial may return a plain token string or accept form encoding; that needs a corresponding client adapter, not an assumption that every /auth/login endpoint is identical.

post<unknown> plus the map checks that the response actually contains a nonempty string token. A TypeScript generic alone would not validate received JSON. This shape check still does not cryptographically validate the JWT. AuthApi returns a cold Observable; the login component’s subscription starts the HTTP request.

Use HTTPS in deployed authentication flows. Keep passwords and tokens out of console logs and URLs. The lab’s disposable alice/mission123 account is a classroom test account, not a credential to embed into MissionApi again.

04 / A fresh layer

Reactive login form: validation, request and feedback

import { Component, DestroyRef, inject, signal } from '@angular/core';
import { HttpErrorResponse } from '@angular/common/http';
import { FormBuilder, ReactiveFormsModule, Validators } from '@angular/forms';
import { Router } from '@angular/router';
import { finalize } from 'rxjs';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { AuthApi } from '../auth-api';
import { TokenStore } from '../token-store';
@Component({
  selector: 'app-login-page', standalone: true, imports: [ReactiveFormsModule],
  templateUrl: './login-page.html',
})
export class LoginPage {
  private readonly fb = inject(FormBuilder);
  private readonly authApi = inject(AuthApi);
  private readonly store = inject(TokenStore);
  private readonly router = inject(Router);
  private readonly destroyRef = inject(DestroyRef);
  protected readonly error = signal<string | null>(null);
  protected readonly pending = signal(false);
  protected readonly loginForm = this.fb.nonNullable.group({
    username: ['', Validators.required], password: ['', Validators.required],
  });
  protected submit(): void {
    if (this.pending()) return;
    this.error.set(null);
    if (!this.loginForm.valid) { this.loginForm.markAllAsTouched(); return; }
    const { username, password } = this.loginForm.getRawValue();
    this.pending.set(true);
    this.authApi.login(username, password).pipe(
      takeUntilDestroyed(this.destroyRef),
      finalize(() => this.pending.set(false)),
    ).subscribe({
      next: response => {
        this.store.setToken(response.accessToken, username);
        this.loginForm.controls.password.reset('');
        void this.router.navigate(['/holdings']);
      },
      error: (error: unknown) => {
        this.error.set(error instanceof HttpErrorResponse && error.status === 401
          ? 'Invalid username or password.'
          : 'Login could not be completed. Check the service and try again.');
      },
    });
  }
}

The form starts blank and uses required on both fields. Invalid submission marks controls touched, reveals errors and sends no request. The pending flag blocks duplicate login requests; finalize clears it after completion, error or cancellation. takeUntilDestroyed ties this request subscription to the component lifetime.

On success, store the token and the entered username, clear the password field, then navigate to holdings. The username is a display value, not trusted proof of identity or authorization. The backend’s validated claims determine access.

The PDF shows one generic credentials error for every failure. Here a 401 gets that message; transport errors or a malformed response get a service-level message. A network failure is not proof the password was wrong. Preserve useful feedback without exposing internal server details.

05 / A fresh layer
Interceptor: immutable request cloning and forward progress
import { inject } from '@angular/core';
import { HttpInterceptorFn } from '@angular/common/http';
import { TokenStore } from './token-store';
import { targetsMission } from './api-urls';
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(TokenStore).getToken();
  if (token && targetsMission(req.url)) {
    return next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }));
  }
  return next(req);
};
export const UI_ORIGIN = 'http://localhost:4200';
export const AUTH_URL = 'http://localhost:3000/auth/login';
export const MISSION_SERVICE_BASE = 'http://localhost:8090';
// Class-room APIs are absolute URLs. Match origin, NOT a raw string prefix.
export function targetsMission(rawUrl: string): boolean {
  try {
    const url = new URL(rawUrl, UI_ORIGIN);
    return url.origin === new URL(MISSION_SERVICE_BASE).origin
      && !url.username && !url.password;
  } catch { return false; }
}
An interceptor receives req and next. It reads the shared store, selects the destination, clones the request with a header, and returns next’s response Observable. HttpRequest and headers are immutable in this API; setting a property on req directly is the wrong mechanism. clone leaves the original request unchanged.
Register the functional interceptor in the application’s HttpClient provider. It applies to requests through that configured client, including generated services that use the same client. It does not intercept a separate browser fetch call. A separately configured child client may have a different interceptor chain.
import { ApplicationConfig, provideBrowserGlobalErrorListeners } from '@angular/core';
import { provideRouter } from '@angular/router';
import { provideHttpClient, withInterceptors } from '@angular/common/http';
import { authInterceptor } from './auth-interceptor';
import { routes } from './app.routes';
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    provideRouter(routes),
    provideHttpClient(withInterceptors([authInterceptor])),
  ],
};
Merge the provider change into app.config; preserve router and other existing providers. Avoid registering conflicting duplicate HttpClient configurations. If your generated client has its own credential option, remove the leftover manual bearer attachment so this lesson has one source of truth.
06 / A fresh layer
Scope tokens to the intended destination
The PDF’s startsWith check separates mission requests from login requests. Removing it affects the second login request in the same running app: the token from the first login now exists, so an unscoped interceptor sends it to /auth/login too. Unrelated APIs could also receive the bearer token. An extra login header may be ignored or rejected depending on the auth server; failure is not guaranteed.
A raw string prefix has another weakness. A URL such as http://localhost:8090.evil.example/orders starts with the base string but targets a different host. The downloadable helper parses the URL and compares the exact scheme, host and port through origin. It also rejects user-info in the URL. The entire trusted mission origin is selected here; if you host multiple APIs under one origin, also apply a path boundary allowlist.
Relative URLs resolve against the explicit classroom UI origin in this example, so they do not target the mission origin. If using a dev proxy or a different deployed topology, deliberately adapt that policy and its tests. Adding an interceptor does not bypass browser CORS requirements.

07 / A fresh layer
Guard: allow navigation or return a redirect
import { inject } from '@angular/core';
import { CanActivateFn, Router } from '@angular/router';
import { TokenStore } from './token-store';
export const authGuard: CanActivateFn = () => {
  const store = inject(TokenStore);
  const router = inject(Router);
  return store.isAuthenticated() ? true : router.createUrlTree(['/login']);
};
import { Routes } from '@angular/router';
import { authGuard } from './auth-guard';
export const routes: Routes = [
  { path: '', redirectTo: 'holdings', pathMatch: 'full' },
  {
    path: 'holdings', canActivate: [authGuard], title: 'Holdings | Mission Control',
    loadComponent: () => import('./holdings-summary/holdings-summary')
      .then(m => m.HoldingsSummary),
  },
  {
    path: 'orders', canActivate: [authGuard], title: 'Place Order | Mission Control',
    loadComponent: () => import('./place-order/place-order')
      .then(m => m.PlaceOrder),
  },
  { path: 'login', title: 'Login | Mission Control',
    loadComponent: () => import('./login-page/login-page').then(m => m.LoginPage) },
  // Optional extension beyond the lab: fallback MUST be last.
  {
    path: '**', title: 'Not found | Mission Control',
    loadComponent: () => import('./not-found/not-found')
      .then(m => m.NotFound),
  },
];
canActivate runs as part of navigation before the protected route is activated and rendered. Return true to continue. Return a UrlTree to ask the router to redirect to login. The PDF navigates imperatively and returns false; the downloadable version uses Angular’s recommended single redirect result. A false result alone cancels navigation and may leave the current route visible rather than necessarily producing a blank page.
Keep login unguarded to avoid redirecting login back to itself. In the simple, non-preloaded loadComponent lab, blocked activation can avoid loading that component. That is not a security promise that guarded code can never be downloaded: preloading or other imports can fetch it. canActivate governs activation; loadChildren recognition and other loading arrangements can have different timing.
The guard checks the TokenStore snapshot when navigation is evaluated. It does not continuously eject a displayed screen whenever a signal changes, so logout explicitly navigates to login. The API remains the authority even if a user edits the guard in DevTools.

08 / A fresh layer
Remove hardcoded login from MissionApi
import { Injectable, inject, signal } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { catchError, finalize, of } from 'rxjs';
import { errorMessage } from './error-message';

export interface OrderRequest {
  ticker: string;
  instrumentType: 'EQUITY' | 'BOND';
  quantity: number;
  price: number;
  side: 'BUY' | 'SELL';
}
// Subset of the course response. Match your server DTO before expanding it.
export interface OrderResponse {
  status: string;
  fee: number;
  newHoldingQuantity: number;
}
const MISSION_URL = 'http://localhost:8090/accounts/1/orders';

@Injectable({ providedIn: 'root' })
export class MissionApi {
  private readonly http = inject(HttpClient);
  readonly lastOrder = signal<OrderResponse | null>(null);
  readonly error = signal<string | null>(null);
  readonly pending = signal(false);

  submitOrder(order: OrderRequest): void {
    if (this.pending()) return; // one in-flight write in this classroom example
    this.pending.set(true);
    this.error.set(null);
    this.lastOrder.set(null);
    this.http.post<OrderResponse>(MISSION_URL, order).pipe(
      catchError((error: unknown) => {
        this.error.set(errorMessage(error));
        return of(null);
      }),
      finalize(() => this.pending.set(false)),
    ).subscribe(response => {
      if (response !== null) this.lastOrder.set(response);
    });
  }
}
This fallback preserves the public submitOrder(request), pending, error and lastOrder contract used by the Module 13 form. It now posts the order once and lets the interceptor attach credentials. There is no login call, embedded password, switchMap login chain or manual Authorization header here.
If continuing with Module 12’s generated OrderControllerService, retain its generated order method and use the same interceptor-configured HttpClient. Match its DTO and response names to your actual generated files. The fallback shown here is direct HttpClient source, not generated code.
A 401 means the server did not accept authentication; a 403 commonly means the identity lacks permission. Keep backend messages curated and business validation intact. This module does not implement refresh tokens, automatic refresh, revocation or automatic order retries. Reconcile uncertain write outcomes before submitting again.

The shell reads the same TokenStore and shows the username while a token is present. Logout clears that store and navigates to login; future mission requests no longer receive this token. Clear account-specific cached data and coordinate in-flight requests when extending this into a multi-user application. Hiding a badge is not the same as clearing its root-service data.
Correction to the supplied model-answer wording: an in-memory token is not immune to XSS. Malicious JavaScript running in the same page may steal it or issue authenticated actions while the session is live. Avoiding persistence reduces how long a stored credential survives, but does not isolate the running app from injected code.

Model answers and evidence limits
A second login can pick up the first token when the URL scope is removed. The correct policy keeps login and mission requests separate. Token presence is only local UI state; API verification determines actual access. Refresh clears this module’s memory token. Persisting a JavaScript-readable token introduces a durable readable credential, while memory still permits XSS attacks during the active session.
The PDF reports a real guarded redirect, intercepted order and database change. This tutorial’s offline models are simulations; they do not claim to have run your Node auth, Spring service, Angular toolchain or Postgres.
