The Final REST Showdown

The database is loaded, the JPA mappings are already in place, and the starter REST controller shows one working repository-backed example. Your job is to build the real API twice with GitHub Copilot: first under a strict one-repository constraint, then again using a more conventional Spring Data design.

The challenge

The model, JPA mappings, repository, startup loader, H2 database, and starter REST code are already provided. This exercise is now entirely about building the API with Copilot and understanding the design decisions Copilot proposes.

  • V1: create a new controller at /v1 and use CustomerRepository as the only repository.
  • V1: navigate from Customer → Purchase → Product with ordinary Java loops.
  • V1: do not use streams, lambdas, Collectors, or additional repository classes.
  • V2: create a second controller at /v2 and remove the repository restriction.
  • V2: let Copilot propose repositories, DTOs, services, queries, validation, and a better persisted refund model.
  • Both versions: keep openapi.yaml synchronized with the API you actually build.
THE RULES

Rules of engagement

V1: only CustomerRepository may access persistence.
V1: ordinary loops only. No streams or lambdas.
V1: Copilot may add new find... methods to CustomerRepository.
V2: Copilot may create any sensible repository or supporting type.
/customers/by-name is reference code only. Do not recreate it.
Never invent refund history that the current model did not persist.
Core idea: V1 asks, “How much can I do through one aggregate root?” V2 asks, “Now that I understand the object graph, how should this application normally be designed?”

Object model at high noon

V1 is built around this path. You begin with CustomerRepository, obtain Customer objects, then navigate their purchases and each purchase's products.

V1 Copilot starter prompt

I am creating a Spring Boot REST API using JPA.

For Version 1, I am only allowed to access persistence through CustomerRepository.

Customer contains purchases and each Purchase contains products.

Do not create ProductRepository, PurchaseRepository, RefundRepository, EntityManager code, or any other repository.

Do not use StoreRestMockData.

When I need purchases or products, start with CustomerRepository and navigate the associated Java objects.

Do not use streams, lambdas, Collectors, map(), filter(), flatMap(), or reduce().

Use ordinary for loops, if statements, ArrayList and LinkedHashMap so the code is easy for beginning Java programmers to understand.

You may add useful Spring Data find methods to CustomerRepository.

Do not implement customers/by-name. That existing method is only a reference example.

V1 · The one-repository challenge

Create a new controller:

@RestController
@RequestMapping("/v1")
public class MyRestController {

    private final CustomerRepository customerRepository;

    public MyRestController(CustomerRepository customerRepository) {
        this.customerRepository = customerRepository;
    }
}

V1 · Customers and cities

  1. Implement GET /v1/customers using customerRepository.findAll().
  2. Support optional ?city=Boston filtering with a normal loop.
  3. Ask Copilot whether findByAddressCityIgnoreCase(...) would be a useful derived query in CustomerRepository.
  4. Implement GET /v1/customers/{customerId} using findById(...) and 404 handling.
  5. Implement GET /v1/cities with unique city names and customer counts.
  6. Implement GET /v1/cities/{city}/customers.
  7. Implement GET /v1/cities/{city}/purchases by finding customers in the city and then walking their purchases.

V1 · Purchases and products

  1. Implement GET /v1/customers/{customerId}/purchases.
  2. Implement GET /v1/purchases with optional customerId and city filters.
  3. Implement GET /v1/purchases/{purchaseId} using nested loops.
  4. Implement GET /v1/products with optional case-insensitive ?name=mouse filtering.
  5. Implement GET /v1/products/{productId} by walking customers, purchases, then products.
  6. Calculate purchase totals as quantity * price with loops.
Ask Copilot whether methods such as findDistinctByPurchasesId(...) or findDistinctByPurchasesProductsId(...) could make lookup easier while still keeping CustomerRepository as the only repository.

V1 · Response design challenge

For at least three endpoints, ask Copilot to compare these approaches:

return customer;

versus a deliberately shaped response:

Map<String, Object> response = new LinkedHashMap<>();
response.put("id", customer.id);
response.put("name", customer.name);
response.put("zip", customer.address.zip);
response.put("city", customer.address.city);
  • Ask what JSON each approach produces.
  • Ask whether bidirectional JPA links can cause recursive or noisy JSON.
  • Ask why a REST representation does not need to match a JPA entity.

V1 · The refund trap

Do not immediately implement the refund endpoints. Ask Copilot whether the current database actually stores historical refunds. 

Examine Customer, Purchase, Product and the existing refund-processing code.

Can the persisted database reconstruct historical refunds after the refund has already been applied?

Do not invent data. Explain what information is lost and what the REST API should do in V1.
A partial refund reduces Product.quantity. A full refund can remove the Product entirely. Current state is not the same thing as historical transaction data.

V1 · Ask about write operations

For every GET endpoint, ask Copilot whether a sensible POST, PUT, or DELETE operation belongs with that resource.

Is there a sensible POST, PUT or DELETE operation related to this resource?

Do not add an operation simply because REST supports that verb.

Only recommend an operation if it makes sense for the domain.

For V1, any implementation must still use CustomerRepository as the only repository.

Reasonable examples may include:

OperationV1 idea
POST /v1/customersCreate a Customer and save with CustomerRepository.
PUT /v1/customers/{id}Find the Customer, update it, save the Customer.
POST /v1/customers/{id}/purchasesFind the Customer, add a Purchase, save the Customer.
POST /v1/customers/{id}/purchases/{purchaseId}/productsWalk to the Purchase, add a Product, save the Customer.
PUT /v1/products/{productId}Walk the graph, update the Product, save the owning Customer.
DELETE /v1/products/{productId}Walk the graph, remove the Product, save the Customer.
ROUND TWO

V2 · Remove the repository restriction

V1 proves that related data can be reached through the Customer object graph. V2 asks how the application should be designed when that artificial restriction is removed. 

I already implemented V1 using CustomerRepository as the only repository.

For V2, remove that artificial restriction.

Create a new controller rooted at /v2.

You may create additional repositories, services, DTOs, request objects, response objects, derived queries, JPQL queries, validation, transaction boundaries, and new persistent entities when they improve the design.

Do not change things merely to make the architecture bigger.

Explain why each new abstraction is useful.

Do not implement customers/by-name. That existing method is only a reference example.

V2 · Let Copilot propose the architecture

Before asking for code, ask Copilot what it would introduce and why.

  • PurchaseRepository?
  • ProductRepository?
  • RefundRepository?
  • Service layer?
  • DTOs or Java records?
  • Request objects?
  • Custom queries?
Do not automatically accept every class Copilot proposes. Ask: “What problem does this class solve, and is it worth the extra abstraction?”

V2 · Build resource-specific repositories

Compare V1 traversal with direct V2 repository access.

// V1 idea
for (Customer customer : customerRepository.findAll()) {
    for (Purchase purchase : customer.purchases) {
        // locate a purchase
    }
}

// V2 idea
purchaseRepository.findById(purchaseId);

Ask Copilot to create useful query methods such as:

findByCustomerId(...)
findByCustomerAddressCityIgnoreCase(...)
findByNameContainingIgnoreCase(...)

Then ask which are derived queries, which need JPQL, and which should simply use inherited JpaRepository methods.

V2 · Replace Maps with typed API models

V1 deliberately used maps to make response construction obvious. V2 should consider typed responses.

public record CustomerResponse(
    Long id,
    String name,
    String zip,
    String city
) {}

Ask Copilot to consider:

  • CustomerResponse
  • PurchaseResponse
  • ProductResponse
  • CityResponse
  • StoreSummaryResponse
  • separate create/update request objects

V2 · Add a service layer where it helps

Ask Copilot whether controllers are doing too much.

Controller
    |
    v
Service
    |
    +--> CustomerRepository
    +--> PurchaseRepository
    +--> ProductRepository
    +--> RefundRepository

Move business logic, validation, calculations, and transactional write operations out of the controller when that makes responsibilities clearer.

V2 · Solve refunds properly

The current model changes or deletes Products when a refund occurs, so historical refund information is not retained. V2 may change the data model. 

Design a persistent Refund model.

A refund should preserve enough historical information to answer the REST API later, even if the Product is changed or removed.

Explain which values should be relationships and which should be historical snapshot fields.

Then create the repository and update refund processing so successful refunds are persisted.

Then implement real V2 refund endpoints such as:

GET /v2/refunds
GET /v2/refunds/{refundId}
GET /v2/customers/{customerId}/refunds
GET /v2/cities/{city}/refunds

V2 · Go beyond CRUD

  • Ask whether summary totals should be calculated in Java or with database aggregation.
  • Ask Copilot to explain the N+1 query problem using Customer, Purchase, and Product.
  • Investigate JOIN FETCH or @EntityGraph only if needed.
  • Revisit whether every association should still be EAGER.
  • Ask where @Transactional belongs.
  • Add request validation such as @NotBlank, @Positive, and @Valid.
  • Consider centralized exception handling with @RestControllerAdvice.

Victory conditions

The application starts and H2 contains the imported data.
A new MyRestController exposes the V1 API.
V1 uses only CustomerRepository.
V1 uses loops rather than streams.
A V2 controller exposes the same core resources with a less constrained design.
V2 introduces only abstractions you can explain and justify.
Refund history is not fabricated in V1 and is properly modeled if implemented in V2.
openapi.yaml accurately documents both versions.

Final word from the sheriff

V1 proves you understand the JPA object graph. V2 proves you can improve the design without blindly accepting whatever Copilot generates. Build it, test it, compare it, and make the AI explain itself.
