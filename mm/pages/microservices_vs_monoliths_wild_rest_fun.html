First things first

What are we actually comparing?

A monolith is not automatically old or bad, and microservices are not automatically modern or better. The useful question is: what boundary makes sense for this system, this team, and this operational environment?

🏠
One big ranch house

Monolith

  • One deployable unit containing multiple business capabilities.
  • One process and codebase, usually with a shared database.
  • Components call each other directly through normal in-process method calls.
  • Sprint 5's engine was small, but structurally it was a monolith.
🏘️
A town of specialists

Microservice

  • A small service built around one business capability.
  • It owns its data and is independently deployable.
  • Other services communicate with it over a network, commonly HTTP or messaging.
  • A microservice architecture is a larger system made from many such services.
The architectural showdown

Every boot has a tradeoff

The PDF frames this as a tradeoff discussion. Monoliths are easier to run and reason about at small scale. Microservices gain deployment and ownership independence, but introduce distributed-system complexity.

🏠 Monolith

What it makes easier
  • One thing to start, debug, and deploy.
  • No network calls between components.
  • Cross-system transactions are simpler with one database and transaction manager.
  • Often easier for a small team to understand.
Where it can hurt
  • Everything deploys together.
  • Everything scales together.
  • The codebase gets harder to own as it grows.
  • A bad dependency or failure can affect the whole application.

🏘️ Microservices

What they unlock
  • Independent deployment.
  • Independent scaling.
  • Clear service ownership.
  • Better failure isolation.
  • Technology can vary by service when justified.
What they cost
  • Method calls become network calls.
  • Data consistency across services is harder.
  • More things must be deployed, secured, observed, and debugged.
  • End-to-end testing requires several services working together.
⭐

So which one is better?

Neither by default. Sprint 5 was correctly a monolith because it was small, owned by one team, and had no need for independent scaling. Sprint 6 has a concrete reason for a service boundary: the order engine needs to be separately deployable and separately securable inside a larger system.

Sprint 5 becomes Sprint 6

Same brain, new boundary

The important design idea is that the core business logic does not need to be rewritten. The environment around it changes.

Sprint 5's SOLID work pays off here. Business classes that do not know about HTTP, Postgres, or JWTs can keep doing the same job when the transport changes.

🌐

HTTP boundary

Orders now arrive over a network through REST endpoints rather than from a CSV-driven application flow.

CSV flow → HTTP request
🗄️

Persistent data

Client, portfolio, and holding data moves from in-memory state to Postgres through MyBatis.

Map → Postgres
🔐

Authentication

Network callers are no longer implicitly trusted. Requests must carry a JWT that can be validated.

Trusted process → JWT
📦

Deployment

The service becomes something that can be independently packaged, containerised, deployed, and operated.

Java app → deployable service

QUIZ ALERT

Know what becomes new when a monolith becomes a service

Students are explicitly tested on this distinction. Turning the existing order engine into a networked service introduces concerns that did not exist in the same way when everything ran as one trusted Java process. The core fee-calculation logic is not one of those new concerns.

NEWRequest / response contract
NEWPersistence across service lifetime
NEWAuthentication and authorisation
NOT NEWCore business arithmetic

Module summary

Architecture is a tradeoff

Microservices gain independent deployment, scaling, and ownership, but they add network, data, testing, and operational complexity.

2

Business logic can survive the move

OrderValidator, OrderProcessingEngine, and HoldingUpdater remain internal domain logic instead of becoming HTTP-aware classes.

The boundary is the lesson
