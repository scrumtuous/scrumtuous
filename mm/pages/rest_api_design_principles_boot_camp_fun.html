1 • The biggest rule

Resources are nouns. HTTP methods are the verbs.

The URL identifies the thing you are working with. The HTTP method says what you want to do to it. That keeps an API consistent and predictable.

Wrong formation

Actions baked into the URL

GET /getAllOrders POST /createOrder POST /deleteOrder/123 GET /updateOrderStatus?id=123&status=REJECTED

The URLs are trying to describe actions. Worse, the final GET changes server state.

Mission approved

One resource, multiple operations

GET /orders GET /orders/{id} POST /orders PATCH /orders/{id}/status DELETE /orders/{id}

/orders names the resource. The method communicates the action.

Exam connection: the supplied quiz specifically tests a legacy endpoint like GET /cancelOrder?id=42. The most important problem is not the spelling of the path. It is that GET changes server state. GET should be safe and should not mutate the resource.

Field Drill: Which endpoint is designed best?

You need to cancel order 42 by updating only its status. Pick the best shape.

2 • HTTP methods

Every method has a job

GET

Read a resource. Do not change server state.

Idempotent: YES

POST

Create a new resource or submit a non-idempotent command.

Idempotent: NO

PATCH

Apply a partial update, such as changing an order status.

Often idempotent when setting a field to a specific value

DELETE

Remove a resource.

Idempotent: YES
🥾
Army BootGET keeps the line disciplined.
New RockPOST can create something brand new.
Moon BootPATCH changes only what needs changing.
Cowboy BootDELETE rides the resource off into the sunset.
3 • Status codes

Status codes should tell the truth

Do not return 200 for every outcome and hide failure inside the JSON body. HTTP already gives clients a compact language for what happened.

200OK

GET succeeded.

201Created

POST created a resource.

204No Content

DELETE succeeded.

404Not Found

The id does not exist.

400Bad Request

Coming with DTO validation.

201 Created should point to the new resource

The Location header gives the client the URL of what was just created.

@PostMapping public ResponseEntity<OrderRecord> create( @RequestBody OrderRecord incoming) { var created = ...; URI location = URI.create("/orders/" + id); return ResponseEntity.created(location) .body(created); }

Why that matters

1
Client POSTs
POST /orders
2
Server returns 201
The resource now exists.
3
Location points to it
Location: /orders/123
Quiz hint: remember the pair POST → 201 Created, and remember that the Location header points at the newly created resource.
4 • Idempotency

Can I safely repeat the request?

Idempotent means that repeating the same request does not keep changing the final server state. This matters when networks fail and clients retry.

The mental model

GET: repeat it. You are only reading.

DELETE: repeat it. The second attempt can return 404, but the resource is still gone.

POST: do not blindly repeat it. You may create a duplicate.

Quiz hint: GET and DELETE are idempotent in this module. POST is not.

5 • Versioning

Plan for change before change becomes a crisis

URI versioning

GET /v1/orders GET /v2/orders

Visible and easy to understand. The trade-off is that every client URL includes the version.

Header versioning

Accept: application/vnd.mission.v1+json

The URL stays stable, but implementation and client configuration become more complex.

Boot Camp reminder: "We have never needed versioning" is not the same as having a plan for the first breaking change.
6 • Bad API field exercise

Bad version → test it → understand the failure → fix it

Bad version

GET /updateOrderStatus?id=123&status=REJECTED HTTP/1.1 200 OK {"success": true}

A browser prefetch, crawler, cache, or monitoring tool may assume GET is safe. This endpoint can mutate an order by accident.

Fix

PATCH /orders/123/status Content-Type: application/json {"status":"REJECTED"} HTTP/1.1 200 OK

Now the method communicates that state changes, the URL remains resource-based, and the outcome is explicit.

Lab: Critique and redesign a real bad API

  • Find at least six separate design problems.
  • Name the REST principle each one violates.
  • Redesign the resource paths and HTTP methods.
  • Assign meaningful status codes.
  • Document which operations are idempotent.
