01 / A fresh layer

One application, two destinations

Downtown Boston has more than one breakfast stop. Your application needs more than one screen too. The crew keeps its shared pancake table while Angular changes the view inside the router outlet.

Based on 14RoutingFundamentals.pdf, Lab 14 and the supplied Sprint 9 quiz. Start with mission-ui from Module 13, where HoldingsSummary and PlaceOrder are shown directly in App. This lesson moves them to /holdings and /orders.

The browser first loads the Angular application. After that, Angular’s router chooses a view from its route configuration. A client route is not a Spring Boot API endpoint: localhost:4200/orders is a UI destination; localhost:8090/accounts/1/orders receives the HTTP order request.

02 / A fresh layer

Define routes and read every part of the configuration

import { Routes } from '@angular/router';
export const routes: Routes = [
  { path: '', redirectTo: 'holdings', pathMatch: 'full' },
  {
    path: 'holdings', title: 'Holdings | Mission Control',
    loadComponent: () => import('./holdings-summary/holdings-summary')
      .then(m => m.HoldingsSummary),
  },
  {
    path: 'orders', title: 'Place Order | Mission Control',
    loadComponent: () => import('./place-order/place-order')
      .then(m => m.PlaceOrder),
  },
  // Optional extension beyond the lab: fallback MUST be last.
  {
    path: '**', title: 'Not found | Mission Control',
    loadComponent: () => import('./not-found/not-found')
      .then(m => m.NotFound),
  },
];

Routes is Angular’s TypeScript configuration type. Each object says which path to recognize and what to do with it. Configured paths omit the leading slash; links can use a leading slash for an absolute app path. '' is the empty string, not a space. redirectTo sends root navigation to the intended starting screen.

loadComponent is a function returning a dynamic import Promise. The import path points to your component file, and .then(m => m.PlaceOrder) selects its named export. Match the file and exported class exactly. Standalone components keep their own template dependencies in their imports; routing does not remove the need for ReactiveFormsModule inside PlaceOrder.

The optional wildcard ** goes last. Route titles update the document title for meaningful navigation. The RouterOutlet must exist in the shell; a route definition alone does not create a display location.

Remove HoldingsSummary and PlaceOrder from App’s direct imports and remove their component tags from app.html. Keep the shared PortfolioBadge outside the outlet. Add RouterOutlet, RouterLink and RouterLinkActive to App’s component imports. Keep the existing provideRouter(routes) in app.config alongside the HTTP and other providers.

import { provideRouter } from '@angular/router';
import { routes } from './app.routes';
// In your EXISTING ApplicationConfig providers array:
provideRouter(routes),
// Preserve your other providers, including HTTP configuration.

RouterOutlet marks where the router inserts an activated component. The shell remains mounted during ordinary navigation between these two routes. Keep the holdings service at providedIn: 'root' if its state must be shared; adding a new provider to a route/component can change the injector scope and give you another instance.

A routed component is normally destroyed when you leave for a different component and recreated when you return. Root-service state can survive that transition; the local FormGroup draft may not. Cached code is not a cached component instance. Preserve a draft explicitly in a suitable service if that behavior is required.

04 / A fresh layer
The crucial empty-path redirect: full versus prefix
pathMatch: 'full' makes this redirect apply only when the whole remaining path is empty. A prefix is a start-of-path match; the empty prefix is present at the start of every path, including orders. This is why an empty-path redirect needs a deliberate matching strategy.
PDF and lab behavior: omitting pathMatch in the Angular 21 development setup triggers NG04014 at configuration validation. The router does not reach a successful /orders navigation. This is a runtime configuration diagnostic, not a TypeScript syntax error. It is more precise than describing only an infinite loop or silent redirect.
// Correct root redirect:
{ path: '', redirectTo: 'holdings', pathMatch: 'full' }
// Deliberately broken exercise in the lab development setup:
{ path: '', redirectTo: 'holdings' }
// Diagnostic: NG04014 ... please provide 'pathMatch'.
The supplied quiz’s older answer describes unwanted prefix redirects if pathMatch is removed. Keep the conceptual reason, but use the PDF’s actual development diagnostic when discussing the omitted property. Explicitly setting prefix is a separate bad configuration choice for this root redirect. Do not generalize a development diagnostic to every production build; keep the correct full match in all builds.

05 / A fresh layer
Lazy loading: deferred code and the trade-off
An eager route statically imports its component. A lazy route uses a dynamic import boundary so the build can separate code required later. The PDF simplifies eager loading as one initial file; actual builds can emit multiple initial/shared files. The useful distinction is what the initial screen must download versus what is deferred.
// Eager route, reading comparison only:
import { PlaceOrder } from './place-order/place-order';
{ path: 'orders', component: PlaceOrder }

// Lazy route used in this lab:
{ path: 'orders', loadComponent: () =>
  import('./place-order/place-order').then(m => m.PlaceOrder) }
Lazy loading can shrink the initial payload for users who never visit Orders. The first visit to Orders can pay an extra request and download delay. If nearly every user immediately opens that screen, eager loading or preloading may provide a better experience. Downloading code is separate from fetching the screen’s data.
After a successful load, the router/module loader can reuse that code in the same app session. Revisiting does not normally fetch the same lazy chunk again. A hard reload creates a new app lifetime; browser HTTP caching, service workers, dev-server changes and deployment hashes can affect what requests you observe. Do not treat “once” as a lifetime guarantee across reloads.

import { provideRouter, withPreloading, PreloadAllModules } from '@angular/router';

In modern Angular, router preloading can include eligible loadComponent routes as well as loadChildren routes. It fetches code in the background after navigation, trading bandwidth for faster later navigation. Do not enable it during the lab’s initial on-demand Network demonstration, or the Orders chunk may already be present.
06 / A fresh layer
Verify code splitting with build output and Network evidence
  1. Run npx ng build. Inspect the Initial chunk files and Lazy chunk files sections. Look for the two routed features in the lazy output.
  2. Remove any leftover direct imports/tags from App. A static reference elsewhere can undermine the intended deferred dependency graph.
  3. Start npx ng serve --port 4200, open DevTools Network, filter JavaScript, clear the log, then reload /holdings.
  4. Before navigating, inspect which code is already fetched. Without configured preloading, Orders should not be activated or fetched simply because a link exists.
  5. Click Place Order. Observe the route URL and the newly required chunk. Return to Holdings, then Orders: loaded code should be reused in this app session.
Chunk names and sizes are not fixed. The source lab reports 42.62 kB for PlaceOrder and 1.97 kB for HoldingsSummary, but those are its example build, not this page’s measurements. Production build output and dev-server Network filenames can differ. For the strongest comparison, inspect a correctly hosted production build with its SPA fallback.
Clear the log before a fresh reload rather than clearing it after the chunk has already loaded. Cache hits still may appear in Network. The key is whether a new deferred request is needed on first activation and whether later activation reuses loaded code.
07 / A fresh layer
routerLink, active links, and programmatic navigation
For a normal unmodified click, routerLink asks Angular to navigate within the app. A plain href to /orders normally requests a new document and reloads the application. RouterLink still supports link semantics, including opening a link in a new tab where appropriate. Use real anchors for navigation, not click-only spans.
routerLinkActive adds a class when a link matches the current URL. The exact option prevents a parent link from remaining active for every deeper child path when that is not intended. ariaCurrentWhenActive="page" communicates the current destination to assistive technology.
import { inject } from '@angular/core';
import { Router } from '@angular/router';
// Inside the component class:
private readonly router = inject(Router);
protected goToOrders(): void {
  void this.router.navigate(['/orders'], { queryParams: { side: 'BUY' } });
}
// Relative navigation requires an ActivatedRoute context:
// this.router.navigate(['details'], { relativeTo: this.route });
A query parameter does not automatically populate the form. Read and validate it deliberately. The router handles browser Back and Forward with its URL history. Avoid changing the address bar yourself while bypassing router state.

Route order, parameters and a not-found destination
Put specific routes before more general patterns. For guests/new, a preceding guests/:id could capture the string “new” as an ID. A wildcard placed first masks all your named routes. Actual nested matching is more complex than this editor’s whole-path comparison, but the ordering lesson transfers.

09 / A fresh layer
Deep links, refresh, and where hosting enters the picture
Inside an already-running app, /orders navigation is handled by Angular. Opening /orders directly or refreshing sends a document request to the host first. The host must return the Angular index.html for valid client-side paths so the router can boot and recognize /orders. Without that SPA fallback, a route that works by clicking can return a server 404 on refresh.
Keep asset files and backend API routes out of the fallback rewrite. Preserve the index base href for your deployment location; hosting under a subdirectory needs corresponding base-path configuration. Hash routing is another explicit deployment option, not required by this lab.
This tutorial’s own course navigation links are ordinary static HTML file links. The editable previews model routing offline. The actual Angular files run in your mission-ui project and need its real build and hosting configuration.
Lazy loading organizes downloads. A route guard controls client navigation. Neither replaces backend authorization. Module 15 adds login, interceptors and guards; the mission endpoint must still validate the token and permissions independently.

Model answers and diagnostic notes
The full root redirect matches only an empty remaining path. Omitting pathMatch in the supplied Angular development lab throws NG04014 before the app navigates; explicitly choosing prefix is a different mistake whose matching semantics are too broad here. The supplied quiz’s prefix explanation needs this diagnostic qualification.
Lazy loading can make the first visit slower because the feature code is deferred. It benefits initial load when that code would otherwise ship unnecessarily. Background preloading trades bandwidth for reduced later delay. Root-service data can survive ordinary route navigation, while a destroyed component’s local form typically starts over when recreated.
Use your actual build/Network evidence. The lesson models do not run ng build, activate real Angular routes or fetch actual feature chunks.
