Big idea

Clean Code Is Not New, It Is Now Explicit

You have already used meaningful names, small methods, and dead-code removal. This module turns those habits into a checklist you can apply deliberately.

Important distinction
Clean code is about readability and change-safety, not proof of correctness. Pretty code can still be wrong. Ugly code can still pass every test. The best outcome is readable code that preserves the behavior the tests already protect.
Before

Readable to No One But the Author

Use MadShapes instead of trade-processing code so the smell is easier to see without memorizing the lab answer.

String s(List<Shape> x) {
    int n1 = 0;
    int n2 = 0;
    double a = 0;

    for (int i = 0; i < x.size(); i++) {
        Shape q = x.get(i);

        if (q.calcArea() > 100) {
            n1 = n1 + 1;
        } else {
            n2 = n2 + 1;
        }

        a = a + q.calcArea();
    }

    return "big=" + n1 +
           ", small=" + n2 +
           ", total=" + a;
}
🏷️ Namess, x, q, n1, and n2 explain almost nothing.
🔢 Magic numberWhy does 100 matter? The code gives no clue.
🧰 Too many jobsThe method categorizes, counts, totals, and formats.
🔁 Repeated workcalcArea() is called more than once for the same object.
Clean-code question to ask: can you explain what each name means without a comment? If not, rename before reaching for comments.
After

Same Output, Much Easier to Read

private static final double LARGE_SHAPE_AREA = 100.0;

String buildAreaSummary(List<Shape> shapes) {
    int largeCount = countShapesBySize(shapes, true);
    int smallCount = countShapesBySize(shapes, false);
    double totalArea = calculateTotalArea(shapes);

    return "big=" + largeCount +
           ", small=" + smallCount +
           ", total=" + totalArea;
}

int countShapesBySize(
        List<Shape> shapes,
        boolean large) {

    int count = 0;

    for (Shape shape : shapes) {
        if (isLargeShape(shape) == large) {
            count++;
        }
    }

    return count;
}

boolean isLargeShape(Shape shape) {
    return shape.calcArea() > LARGE_SHAPE_AREA;
}

double calculateTotalArea(List<Shape> shapes) {
    double totalArea = 0.0;

    for (Shape shape : shapes) {
        totalArea += shape.calcArea();
    }

    return totalArea;
}
🏷️Meaningful nameslargeCount tells you what it stores.
✂️One job per methodEach method is explainable in one sentence.
🔢Named constantThe threshold now has a reason-shaped name.
📚One abstraction levelSummary-building code does not contain raw counting details.
💬Fewer comments neededThe names explain what the code is doing.
Behavior preservation: the refactor is only successful if the same inputs still produce the same outputs and the existing tests remain unchanged.
The checklist

Five Areas to Inspect on Any Refactor

🏷️ Naming Do variables and methods explain themselves without a comment?
✂️ Function size Does each method do one job at one level of detail?
🔢 Magic numbers & duplication Are important values named and repeated logic extracted once?
↩️ Control flow Can deep nesting be flattened with an early return or guard clause?
💬 Comments Do comments explain why, rather than narrating what the code already says?

Interactive clean-code checklist

Comments

A Comment Explaining WHAT Is Often a Warning Sign

🚫 Narrates the code

// loop through the shapes and add up the areas

If the code needs this comment to be understandable, the names or method boundaries probably need work.

✅ Explains a reason

// Psychology team requested 100 square units as the first-iteration large-shape cutoff.

This explains why a non-obvious threshold exists.

Rule of thumb
The code should usually explain what it does. Comments earn their place by explaining why.

💬 Comment challenge

Which is better: adding a comment above a confusing block, or extracting that block into calculateTotalArea()?

Usually extract the block into a well-named method.
The method name becomes part of the code and stays closer to the behavior it describes.
Control flow

Prefer Guard Clauses Over Deep Nesting

🚫 Nested
String describeShape(Shape shape) {
    if (shape != null) {
        if (shape.calcArea() > 0) {
            return "measurable";
        } else {
            return "zero area";
        }
    } else {
        return "missing";
    }
}
✅ Guard clauses
String describeShape(Shape shape) {
    if (shape == null) {
        return "missing";
    }

    if (shape.calcArea() <= 0) {
        return "zero area";
    }

    return "measurable";
}
Why it helps
Guard clauses get exceptional or special cases out of the way early, leaving the main path easier to read.
GenAI review

Read a Copilot Refactor Like a Review Comment

A confident-looking suggestion is not automatically better. Evaluate the changes one by one and test the result.

1
Read the diff What actually changed?
2
Apply the checklist Is the code truly clearer?
3
Run unchanged tests Did behavior stay the same?
4
Keep, reject, modify You are allowed to say no.
Direct quiz connection: for a GenAI refactor, run the existing unmodified tests, assess each proposed change against a checklist, and keep only changes that preserve behavior and materially improve readability.
ROFLGator code review "It compiles" is not a readability argument, and it definitely is not proof that the behavior stayed the same.

Critical assessment

Keep, Reject, or Modify Each Suggestion

Suggestion Decision Reasoning
Rename x to shapes Keep The name now says what the variable contains.
Replace 100 with LARGE_SHAPE_AREA Keep The meaning is explicit and the value has one place to change.
Replace loops with streams only because they look shorter Maybe reject Different syntax is not automatically clearer for the team.
Change > to >= at the threshold Reject unless required That changes behavior. Existing tests should expose the edge case.
Watch boundary changes: a refactor that changes > into >=, changes rounding, or handles an empty list differently is no longer behavior-preserving.

🎓 Final challenge

Copilot renames variables well, extracts two methods, and also changes the large-order test from > 10000 to >= 10000. What should you keep, reject, and verify?

Keep:
The meaningful renames and focused method extractions, if they improve readability.

Reject:
The change from > 10000 to >= 10000 unless the requirements explicitly demand it.

Verify:
Run the existing unmodified tests, especially a boundary case at exactly 10000.
