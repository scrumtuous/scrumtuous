Big idea

You Have Already Been Doing the Shape of TDD

Previous labs gave you tests first and implementation second. The missing piece was that you did not write the tests yourself.

Today changes one thing
You write the test first. The test comes before the implementation, every cycle.
The cycle

Red, Green, Refactor

🔴 RED Write one test for one new behavior. Run it. Watch it fail. Read why it failed.
🟢 GREEN Write the smallest code that makes that test pass. Do not guess ahead.
🟣 REFACTOR Improve names or structure while the passing tests protect the behavior.

Cycle 1

The First Green Should Feel Almost Too Easy

Use a MadShapes classifier so the idea stays separate from the official lab.

RED

One fact: area 20 is SMALL

@Test
void classifiesTwentyAsSmall() {
    AreaBandClassifier classifier =
        new AreaBandClassifier();

    assertEquals(
        "SMALL",
        classifier.classify(20)
    );
}

Run it. It fails because classify() does not exist or has no useful implementation.

GREEN

The smallest implementation

public String classify(double area) {
    return "SMALL";
}

This is not laziness. The test has only established one fact. Nothing has earned a branch yet.

Direct exam connection: the constant return is correct in strict TDD for the first test. The next failing test is what forces real conditional behavior.
Jimbo James complains Jimbo James of the Columbian cartel says returning "SMALL" for everything looks suspicious. TDD agrees, but insists he first write the test that proves more behavior is required.
Cycle 2

The Next Test Forces the First Real Branch

RED AGAIN

One new fact: area 300 is LARGE

@Test
void classifiesThreeHundredAsLarge() {
    AreaBandClassifier classifier =
        new AreaBandClassifier();

    assertEquals(
        "LARGE",
        classifier.classify(300)
    );
}

The old return "SMALL"; now fails. Perfect. The new test earned the new logic.

GREEN

Add only the branch you now need

public String classify(double area) {
    if (area >= 300) {
        return "LARGE";
    }

    return "SMALL";
}
Design by pressure
The implementation grows only when a new test proves the old implementation is insufficient.
Boundaries

A Boundary Test Is Evidence, Even If It Passes Immediately

Boundary tests lock down decisions such as > versus >=. They protect exactly the cases that are easy to change accidentally later.

MadShapes example

Suppose 300 square units starts the LARGE band.

299.99
300.00

Boundary question: is exactly 300 SMALL or LARGE?

Why test it?

  • Confirms the intended comparison operator
  • Documents the business decision
  • Catches later regressions
  • Costs very little to write
Boundary tests are not wasted: a test can pass without forcing new code and still be valuable because it records and protects a design decision.

🎯 Boundary challenge

If the rule says "LARGE starts at 300", what comparison should the implementation use?

area >= 300

The boundary is inclusive, so an area of exactly 300 belongs in the LARGE band.
What TDD is really doing

The Next Test Is a Design Decision

🧠 Decide the next behavior The test says what the code should do next.
🤏 Do no more than necessary Avoid building speculative behavior with no demonstrated need.
🧼 Improve design safely Passing tests let you clean structure without losing behavior.
The design-tool idea
TDD controls when complexity is allowed to enter the codebase. Every extra branch, condition, or abstraction should be justified by a behavior you have made visible.
ROFLGator's rule If you catch yourself implementing a future case "because we'll probably need it", stop and make that need visible with a failing test first.
Refactor

Green First, Cleanup Second

Refactoring belongs after the test is green. You are changing structure while intentionally preserving behavior.

REFACTOR
private static final double LARGE_AREA_THRESHOLD = 300.0;

public String classify(double area) {
    if (area >= LARGE_AREA_THRESHOLD) {
        return "LARGE";
    }

    return "SMALL";
}

The named constant improves readability, but the tests should still pass exactly as before.

Clean Code carries forward: red-green-refactor does not replace earlier lessons. Refactor is where naming, constants, and method structure get improved under test protection.

Module 10 Lab: Build FeeBandClassifier Test-First

The official lab uses trade-value bands. Follow the required sequence exactly instead of implementing the full business rule in one go.

3

Boundaries + refactor

5000 is PREMIUM.

50000 is INSTITUTIONAL.

Then extract 5000 and 50000 into named constants.

Exact quiz connection: the Step 1 implementation that returns "STANDARD" unconditionally is not a shortcut. It is the minimum correct green implementation for the behavior currently demonstrated by the test.
Rule to actually follow
If you write implementation code that no current test requires, stop and write the test first. The lab is deliberately about discipline, not about reaching the final answer as fast as possible.
