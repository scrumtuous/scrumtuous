Concept 1

What Is a Class? What Is an Object?

A class is a definition. An object is a real instance created from that definition. Same blueprint, separate objects, separate state.

Think visually
Class
Blueprint
→
new
→
Object
Real instance
MadShapes example
Circle class
→
circleOne
circleTwo
Same class. Two separate objects.
Circle circleOne = new Circle(5);
Circle circleTwo = new Circle(5);

circleOne.getClass() == circleTwo.getClass();  // true
circleOne == circleTwo;                        // false

// Same class, different objects.
// Changing one object does not change the other.
Quiz hint: a class is not the same thing as an object. The class defines the structure and behavior. The object is the actual instance created with new.

If you write Square first = new Square(4); and Square second = new Square(4);, what is true: same class, same object, or both?

They are built from the same class, but they are different objects.
Concept 2

Encapsulation Protects a Real Rule

A private field is not decoration. It protects a rule that must always stay true. That rule is called an invariant.

🚫 Bad version

public class Square {
    public double side;
}

Square s = new Square();
s.side = -10;   // nobody stopped this

The object can drift into nonsense because any caller can write any value.

✅ Better version

public class Square {
    private double side;

    public Square(double side) {
        if (side <= 0) {
            throw new IllegalArgumentException(
                "Side must be positive"
            );
        }
        this.side = side;
    }

    public double getSide() {
        return side;
    }

    public void resize(double delta) {
        double newSide = side + delta;
        if (newSide <= 0) {
            throw new IllegalArgumentException(
                "Side must stay positive"
            );
        }
        side = newSide;
    }
}
Why this matters
The rule is enforced in one place only. Callers do not need to remember to check for invalid state. The object protects itself every time.
Quiz hint: encapsulation is not only about hiding data. It is about protecting a rule such as "quantity cannot go negative" or "a square side length must stay positive."

🛡️ Your challenge

Why is private useful here? Give the practical reason, not the vocabulary-only reason.

It forces all changes to go through methods that can validate the rule.
That makes invalid state much harder or impossible to create.
Concept 3

Inheritance: Reuse With an "Is-A" Relationship

Inheritance uses extends. The subclass gets fields and methods from the superclass, and can override behavior that must differ.

class ShapeV1 {
    String getLabel() {
        return "shape";
    }

    double calcArea() {
        return 0.0;   // default area
    }
}

class PointV1 extends ShapeV1 {
    // calcArea() is inherited unchanged
}

class CircleV1 extends ShapeV1 {
    private double radius;

    CircleV1(double radius) {
        this.radius = radius;
    }

    @Override
    double calcArea() {
        return Math.PI * radius * radius;
    }
}
What inheritance is doing
Inherit what you do not need to change. Override what you do. That is the healthy version of inheritance.
ROFLGator reminder A Circle is a Shape. A Rectangle is a Shape. Those sound like natural sentences, which is a good sign that inheritance may fit.

🔺 Quick check

If a method from the parent class already works for the child class, should you rewrite it anyway?

No.
If the inherited behavior is already correct, keep it and only override what must differ.
Concept 4

The Silent Bug: Forgetting to Override

A concrete superclass can hide a mistake. If the subclass forgets to override a method, the code still compiles and may quietly do the wrong thing.

class ShapeV1 {
    double calcArea() {
        return 0.0;
    }
}

class PointV1 extends ShapeV1 {
    // area 0.0 is fine here, by coincidence
}

class CircleBuggy extends ShapeV1 {
    private double radius;

    CircleBuggy(double radius) {
        this.radius = radius;
    }

    // forgot to override calcArea()
    // compiles fine, but returns 0.0
}
Why it is dangerous
The compiler sees valid Java. It does not know you forgot shape-specific logic. The wrong result appears later when someone notices a strange area.
Quiz hint: concrete inheritance can hide missing overrides. That is one reason abstract classes exist.
Concept 5

Abstract Classes Turn the Silent Bug Into a Compile Error

An abstract class cannot be instantiated directly. It can also force subclasses to provide behavior.

public abstract class Shape {
    private final String label;

    protected Shape(String label) {
        this.label = label;
    }

    public String getLabel() {
        return label;
    }

    public abstract double calcArea();
}

class BrokenCircle extends Shape {
    BrokenCircle() {
        super("circle");
    }
}

// Compile error:
// BrokenCircle must implement calcArea()

Concrete class

Can be instantiated. Can provide a default implementation.

Abstract class

Cannot be instantiated. Can force subclasses to implement key behavior.

Common exam angle: an abstract class is useful when there is a real parent-child relationship and every subclass must supply certain behavior.

🧠 Quick check

Why is abstract double calcArea(); safer than a default return 0.0; for many shapes?

Because every subclass is forced to provide its own area logic.
A missing override becomes a compile error instead of a quiet bug.
Concept 6

Interfaces: A Capability, Not a Family Tree

Use an interface when unrelated classes need to share a capability. The interface says what something can do, not what it is.

public interface Displayable {
    void render();
}

public class CircleShape extends Shape
        implements Displayable {

    private final double radius;

    public CircleShape(double radius) {
        super("circle");
        this.radius = radius;
    }

    @Override
    public double calcArea() {
        return Math.PI * radius * radius;
    }

    @Override
    public void render() {
        System.out.println("Draw a circle");
    }
}

public class InstructionBanner
        implements Displayable {

    @Override
    public void render() {
        System.out.println("Choose the larger area");
    }
}
Why this matters
A banner is not a Shape. But both a shape and a banner can be displayable. The shared capability is what matters.
Quiz hint: interfaces are for capabilities shared across classes that may not belong in the same inheritance hierarchy.
Concept 7

Polymorphism: One Call, Different Behavior

Polymorphism means you can write calling code once against a general type, and the right method runs based on the actual object.

Across an abstract class

List<Shape> shapes = List.of(
    new CircleShape(3),
    new RectangleShape(4, 5),
    new TriangleShape(6, 2)
);

double totalArea = 0.0;

for (Shape shape : shapes) {
    totalArea += shape.calcArea();
}

Across an interface

List<Displayable> screenItems = List.of(
    new CircleShape(3),
    new InstructionBanner()
);

for (Displayable item : screenItems) {
    item.render();
}
Exam-ready idea: the calling code does not need an if/else for every concrete class. That is the payoff of polymorphism.
ROFLGator says hello One loop. Many forms. Much cleaner than writing a branch for Circle, Rectangle, Triangle, and every future shape.

🧠 Quick challenge

Why is a List<Shape> usually better than separate loops for circles, rectangles, and triangles?

Because one loop can call the same method on every shape.
The behavior changes based on the actual object, so the calling code stays simpler.
Concept 8

Recognizing Bad Inheritance

Do not extend a class just because you want its storage or utility methods. The relationship still needs to make sense.

🚫 Bad idea

public class BadShapeRegistry
        extends ArrayList<String> {
}

BadShapeRegistry registry =
        new BadShapeRegistry();

registry.add("Circle");
registry.add("Circle");   // duplicate allowed

A registry is not an ArrayList. This leaks a huge API and gives you poor control over rules.

✅ Better: composition

public class GoodShapeRegistry {
    private final List<String> shapeIds =
            new ArrayList<>();

    public void addShape(String id) {
        if (shapeIds.contains(id)) {
            throw new IllegalArgumentException(
                "Duplicate shape id"
            );
        }
        shapeIds.add(id);
    }

    public boolean contains(String id) {
        return shapeIds.contains(id);
    }

    public int size() {
        return shapeIds.size();
    }
}
Composition in plain English
The registry has a List. It is not a List. That gives the class control over its own public interface.
Likely quiz theme: composition is the better choice when you want reuse without pretending an "is-a" relationship exists.
Jimbo James object model advice Jimbo James of the Columbian cartel wanted CartelRegistry extends ArrayList<String>. This is why we ask the tests, not Jimbo, to review our design choices.
Concept 9

Four Tools, Four Situations

Java gives you multiple OO tools. The trick is matching the tool to the problem.

🏠 Concrete class A real, instantiable thing with working behavior right now.
🧱 Abstract class A real parent-child relationship where subclasses must provide key behavior.
🧩 Interface A shared capability across classes that may not otherwise belong together.
🧺 Composition Reuse another class internally without pretending you are that class.
