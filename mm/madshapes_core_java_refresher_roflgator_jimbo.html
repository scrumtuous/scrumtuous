Concept 1

Why Java Looks So Different

The logic is usually familiar. Java asks you to state more information up front so the compiler can check it.

🐍 Python

  • Dynamically typed
  • Type problems may surface at runtime
  • Indentation marks code blocks
  • Less syntax around each statement

☕ Java

  • Statically typed
  • Types are checked by the compiler
  • Braces mark code blocks
  • Semicolons end most statements
Three exam-ready truths: looking for a Java concept's Python equivalent is often useful, core ideas such as collections and control flow transfer, and Java can catch some type mismatches before the program runs.

🌸 Quick check

Why can Java reject some bad assignments before execution?

Because Java is statically typed.
The compiler knows each variable's declared type and can reject incompatible assignments.
Concept 2

Types: Declared, Not Inferred Away

Once a Java variable is declared with a type, that variable keeps that type.

String shapeName = "Triangle";
int base = 12;
double area = 30.5;
boolean visible = true;

// Python might look like:
// shape_name = "Triangle"
// base = 12
// area = 30.5
// visible = True

Python can rebind the name

size = 10
size = "ten"

Java rejects the mismatch

int size = 10;
size = "ten";  // compile error
MadShapes connection
When we eventually build classes such as Circle and Rectangle, Java's type system gives the compiler useful information about what each variable can refer to.

Concept 3

Control Flow: Same Logic, Different Punctuation

Java if/else uses the same reasoning as Python. Parentheses, braces, and semicolons are the visible differences.

double firstArea = 48.0;
double secondArea = 48.0;

String judgement;

if (firstArea == secondArea) {
    judgement = "SAME";
} else {
    judgement = "DIFFERENT";
}
Scope note
The future psychology feature about perceptual thresholds is not part of this iteration. For this refresher, an exact area comparison keeps the example simple.
Remember: Python uses indentation to define blocks. Java uses braces. The underlying decision logic is still the same.

Concept 5

List<String>: Generic and Compiler-Enforced

Instead of using the course's trade example, MadShapes can keep a typed list of shape names.

List<String> shapeNames = new ArrayList<>();

shapeNames.add("Circle");
shapeNames.add("Triangle");
shapeNames.add("Rectangle");

for (String shapeName : shapeNames) {
    System.out.println(shapeName);
}
Why the angle brackets matter: List<String> gives the compiler a rule it can enforce. An Integer cannot casually wander into this list.

Concept 6

Map and Set: Accumulate and Deduplicate

A Map can accumulate total area by shape type. A Set can keep the distinct shape types used in an experiment.

Map<String, Double> totalAreaByType
        = new HashMap<>();

String type = "Triangle";
double newArea = 24.0;

double currentTotal = totalAreaByType
        .getOrDefault(type, 0.0);

totalAreaByType.put(
        type,
        currentTotal + newArea
);

Set<String> observedTypes = new HashSet<>();
observedTypes.add("Triangle");
observedTypes.add("Circle");
observedTypes.add("Triangle");  // duplicate ignored
Python translation
Java's getOrDefault(key, 0.0) is the same basic idea as Python's dict.get(key, 0.0). The accumulation pattern is familiar even though the spelling changes.

📦 Quick check

What Java method in the example provides a fallback value when the key does not exist?

getOrDefault(key, defaultValue)
Concept 7

Two Categories of Exception

This is the one idea in the refresher that does not map neatly to Python's compiler model: Java divides exceptions into checked and unchecked categories.

Unchecked

Extends RuntimeException

  • The compiler does not force handling
  • You may catch it or let it propagate
  • Example: NumberFormatException
Checked

Extends Exception

  • The compiler requires catch or declaration
  • Callers must acknowledge the possibility
  • No direct Python compiler equivalent
Watch the trap: Java absolutely has exception handling. The special Java concept here is the compiler-enforced checked vs. unchecked distinction.
Concept 8

Unchecked Exception: Bad Shape Input

Suppose a text field supplies a radius. If the text is not numeric, Java's parser throws an unchecked NumberFormatException.

String radiusText = "banana";

try {
    double radius =
        Double.parseDouble(radiusText);
} catch (NumberFormatException e) {
    System.out.println(
        "Radius must be numeric"
    );
}

// The compiler did not force this catch.
// NumberFormatException is unchecked.
MadShapes thinking
The syntax parser and the business rule are different concerns. "banana" is not numeric at all. A numeric value such as -5 can be parsed, but may still violate a dimension rule.

⚠️ Quick check

Does Java force you to catch NumberFormatException?

No.

NumberFormatException extends RuntimeException, so it is unchecked.
The compiler does not require a catch or throws declaration.
Concept 9

Checked Exception: Invalid Dimension

Now use a checked exception for a value that is numeric but violates a rule we want callers to acknowledge.

public class InvalidDimensionException
        extends Exception {

    public InvalidDimensionException(
            String message) {
        super(message);
    }
}

static double parsePositiveDimension(
        String text)
        throws InvalidDimensionException {

    double value = Double.parseDouble(text);

    if (value <= 0) {
        throw new InvalidDimensionException(
            "Dimension must be positive: " + value
        );
    }

    return value;
}
Key distinction: Double.parseDouble() can throw unchecked NumberFormatException. Our explicit InvalidDimensionException is checked, so callers must catch or declare it.

🧠 Quick check

If a method calls parsePositiveDimension() and does not catch InvalidDimensionException, what must it do?

It must declare InvalidDimensionException in its own throws clause.
