Big picture

You Have Only Used a Fraction of JUnit So Far

Basic assertions prove behavior. JUnit 5 also helps you organize setup, document intent, test many inputs, and express exception behavior cleanly.

🔁@BeforeEachFresh setup before every test.
💥assertThrowsFormal exception testing.
🧺assertAllRun several related assertions together.
🧮@ParameterizedTestOne test body, many inputs.
🗂️@NestedGroup behavior into readable contexts.
🏷️@DisplayNameMake the report read like documentation.
Feature 1

@BeforeEach Gives Every Test Fresh State

Shared setup is useful, but shared mutable state between tests is dangerous. @BeforeEach rebuilds the test fixture every time.

private Rectangle rectangle;

@BeforeEach
void setUp() {
    rectangle = new Rectangle(10, 4);
}

@Test
void areaStartsAtForty() {
    assertEquals(40.0, rectangle.calcArea());
}

@Test
void anotherTestGetsAFreshRectangle() {
    assertEquals(40.0, rectangle.calcArea());
}
Why it matters
No test sees another test's leftovers. Tests should pass in any order.
Test design habit: order-dependent tests are a smell. Fresh setup helps each test stand on its own.
Feature 2

assertThrows Tests Exceptions Directly

@Test
void negativeSquareSideThrows() {
    var exception = assertThrows(
        IllegalArgumentException.class,
        () -> new Square(-2)
    );

    assertEquals(
        "Side must be positive",
        exception.getMessage()
    );
}

Manual try/catch risk

A poorly written manual test can accidentally pass when no exception is thrown.

assertThrows

Fails automatically if the expected exception never happens, and gives you the exception object back.

Direct quiz connection: assertThrows is the right formal tool when the required behavior is "this call must throw this exception type."
Feature 3

assertAll Reports Multiple Related Failures Together

@Test
void circleReportsRadiusAndAreaTogether() {
    Circle circle = new Circle(5);

    assertAll(
        "circle properties",
        () -> assertEquals(5, circle.getRadius()),
        () -> assertEquals(
            Math.PI * 25,
            circle.calcArea(),
            0.0001
        )
    );
}
✓ radius equals 5
✓ area equals 78.5398 within tolerance

If both fail, JUnit reports both failures instead of stopping after the first one.

Feature 4

@ParameterizedTest: One Test Body, Many Inputs

@ValueSource

Use when each run changes one input but keeps the same expected rule.

@ParameterizedTest
@ValueSource(doubles = {
    1.0, 5.0, 20.0
})
void positiveSidesCreateValidSquares(
        double side) {

    assertTrue(
        new Square(side).calcArea() > 0
    );
}

@CsvSource

Use when each input has its own expected output.

@ParameterizedTest
@CsvSource({
    "2, 4",
    "3, 9",
    "10, 100"
})
void squareAreaMatchesExpected(
        double side,
        double expectedArea) {

    assertEquals(
        expectedArea,
        new Square(side).calcArea()
    );
}
Exact boundary connection: @CsvSource is especially useful when each row includes input plus expected output, including boundary cases that may differ from nearby values.

Feature 5

@Nested and @DisplayName Turn the Report Into Documentation

@Nested
@DisplayName("when the shape dimensions are invalid")
class InvalidDimensions {

    @Test
    @DisplayName("a negative square side throws")
    void negativeSquareSideThrows() {
        assertThrows(
            IllegalArgumentException.class,
            () -> new Square(-1)
        );
    }
}
when the shape dimensions are invalid
✓ a negative square side throws
Quiz hint: @Nested groups related behaviors, while @DisplayName makes the generated report understandable without opening the source code.
Isolation

What Is a Test Actually Testing?

A test can involve several real classes. When it fails, you may not know which one is responsible.

Real Shape
area formula can fail
→
ExperimentRunner
system under test
→
Real ResultWriter
storage can fail
Problem
One red result, three possible causes. A failure may come from the class under test or from either real collaborator.
Direct quiz connection: real collaborators test a broader integrated behavior, while mocks isolate the class under test so a failure points more directly to its coordination logic.
Mockito

A Mock Is a Collaborator You Fully Control

Mock AreaSource
controlled by test
→
ExperimentRunner
→
Mock ResultWriter
records calls
@ExtendWith(MockitoExtension.class)
class ExperimentRunnerTest {

    @Mock
    private AreaSource mockAreaSource;

    @Mock
    private ResultWriter mockWriter;
}
Mock behavior
A mock does nothing useful until the test tells it what to do. It also remembers how it was called so the test can verify interactions.
Mockito toolkit

Stub, Verify, Count, Capture

🎛️ when(...).thenReturn(...) Control what the collaborator gives back.
✅ verify(...) Prove an interaction happened.
🔢 times(n) Prove it happened exactly n times.
🎣 ArgumentCaptor Capture the actual value, then inspect it flexibly. 
@Test
void runnerUsesWhateverAreaItIsGiven() {
    when(mockAreaSource.areaFor("circle"))
        .thenReturn(42.0);

    double area =
        new ExperimentRunner(mockWriter)
            .run("circle", mockAreaSource);

    assertEquals(42.0, area);

    verify(mockWriter)
        .write("circle: 42.0");

    verify(mockAreaSource, times(1))
        .areaFor("circle");
}
ArgumentCaptor<String> captor =
    ArgumentCaptor.forClass(String.class);

verify(mockWriter)
    .write(captor.capture());

assertThat(
    captor.getValue(),
    allOf(
        containsString("circle"),
        containsString("42.0")
    )
);
Interaction testing: Mockito adds a new kind of assertion. You can verify that a collaborator was called, called exactly once, or never touched at all.
Hamcrest

Readable, Composable Assertions

assertThat(area, is(42.0));
assertThat(area, greaterThan(0.0));

assertThat(
    report,
    containsString("circle")
);

assertThat(
    labels,
    hasSize(3)
);

assertThat(
    area,
    allOf(
        greaterThan(0.0),
        lessThan(100.0)
    )
);
Why people like it
Hamcrest matchers often read closer to the requirement and compose naturally for strings, collections, and ranges.
Do not overuse mocks

Not Every Class Needs Mockito

No collaborators

RiskLimitChecker accepts primitive values and returns a boolean.

Nothing to mock.

Has collaborators

OrderExecutor coordinates an Instrument and a ReportWriter.

Mocking may help isolate it.

Direct exam connection: not every class needs a mock. A primitive-only checker has no collaborator whose real behavior can leak into the test.
ROFLGator testing rule Mock collaborators when isolation helps. Do not mock a number simply because Mockito exists.

🎓 Final challenge

A test uses a real BondInstrument and a real InMemoryReportWriter while testing OrderExecutor. Another test mocks both collaborators. What is the main difference?

The real-collaborator test exercises several classes together, so a failure could come from any of them.

The mock-based test isolates OrderExecutor's coordination logic. If it fails, the cause points much more directly at OrderExecutor itself.
