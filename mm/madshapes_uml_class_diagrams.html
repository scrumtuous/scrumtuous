Concept 1

From Worksheet to Diagram

Your Module 3 worksheet already had entities, responsibilities, and relationships. UML expresses the same ideas with more precision.

Why the notation matters
Precision forces a decision. If you write an open diamond, filled diamond, dashed arrow, or hollow triangle, you are making a specific claim about the relationship.
Concept 2

A Class, in Mermaid

One block per class. A minus sign means private. A plus sign means public.

classDiagram

class Circle {
    -radius double
    +calcArea() double
}

class Rectangle {
    -height double
    -width double
    +calcArea() double
}
Canvas example: UML class boxes
The class name is at the top, attributes in the middle, methods at the bottom.
Visibility hint: -radius means private. +calcArea() means public. This connects directly to encapsulation from Module 2.

Five relationship types

Same Boxes, Very Different Meanings

➡️ Association Holds a reference. "Knows about."

Trial --> Student

◇ Aggregation Loose "has a". The part can outlive the whole.

Experiment o-- Shape

◆ Composition Strong "has a". The part depends on the whole for meaning.

Experiment *-- Trial

△ Inheritance "Is a kind of."

Circle --|> Shape

⇢△ Implements A class satisfies an interface contract.

Circle ..|> Measurable

Key exam habit: decide the meaning first, then the arrow. "Has a" alone is not enough. Ask whether the part can exist independently.
Concept 3

Association: "Refers To"

Association means one class holds a reference to another to do its job. No ownership claim is implied.

classDiagram
class ComparisonTrial
class Student

ComparisonTrial --> Student : answered by
Canvas example: Association
Read it as: ComparisonTrial knows about the Student who answered it.
Multiplicity matters: a student could answer many trials while each trial refers to one student. UML can make that cardinality explicit.
Concept 4

Aggregation: "Has A", Loosely

Aggregation is a whole-part relationship where the part still makes sense without the whole.

classDiagram
class Experiment
class Shape

Experiment o-- Shape : uses
Canvas example: Aggregation
Delete the Experiment and the Circle still makes sense as a Circle.
Quiz test: ask "if I delete the whole, does the part still make sense on its own?" If yes, aggregation is plausible.
ROFLGator memory trick Open diamond, loose ownership. If the whole vanishes, the part can still carry on with its day.
Concept 5

Composition: "Has A", Strongly

Composition is also whole-part, but the part is conceptually tied to the whole.

classDiagram
class Experiment
class ComparisonTrial

Experiment *-- ComparisonTrial : owns
Canvas example: Composition
A ComparisonTrial in this design belongs to an Experiment. Without the Experiment, the trial loses its context.
Classic distinction: open diamond is aggregation, filled diamond is composition. The meaning behind the diamond matters more than the shape itself.
Concept 6

Inheritance: "Is A Kind Of"

Inheritance is the UML version of Java's extends.

classDiagram
class Shape {
    <<abstract>>
    +calcArea() double
}
class Circle
class Rectangle
class Triangle

Circle --|> Shape
Rectangle --|> Shape
Triangle --|> Shape
Canvas example: Inheritance
The hollow triangle points at the parent class.
Quiz clue: "Circle is a kind of Shape" supports inheritance. "Portfolio has Instruments" does not. That is a different relationship.
Concept 7

Interface Realization: Implements a Contract

A class can implement an interface without sharing implementation or belonging to the same family tree.

classDiagram

class Renderable {
    <<interface>>
    +render() void
}

class Circle
class InstructionBanner

Circle ..|> Renderable
InstructionBanner ..|> Renderable
Canvas example: Interface realization
The line is dashed, and the hollow triangle points at the interface.
Exam distinction: interface realization looks similar to inheritance, but the dashed line matters. It means "implements", not "extends".

Bonus relationship

Dependency: "Uses Briefly"

The lab explicitly asks you to distinguish association from dependency. A dependency is temporary use, often through a method parameter, without storing a lasting reference.

classDiagram
class ShapeComparator
class Shape

ShapeComparator ..> Shape : compares
Canvas example: Dependency
Dashed arrow, no hollow triangle. It means "uses", not "implements".
Direct quiz connection: if OrderValidator receives RiskLimit only as a method parameter and does not retain it, that is a dependency, not a permanent association.

Read critically

Precise Does Not Automatically Mean Correct

🔎 Does every class trace back to the worksheet or a clearly explained design need?
🔗 Is every permanent reference really an association?
◇ Is a "has a" relationship truly aggregation?
◆ Should that "has a" actually be composition?
△ Does every inheritance arrow describe a real "is a" relationship?
🧩 Are interfaces expressing capabilities instead of forced family trees?
Important reasoning: a neat diagram can still model the wrong relationship. Peer review exists partly to challenge diagrams that look polished but encode weak design decisions.
Why Mermaid?

Diagrams as Text Stay Close to the Codebase

Text source

  • Diffs cleanly in Git
  • Easy to review in a pull request
  • Lives beside the rest of the project
  • Can be rendered automatically

Rendered image

  • Useful in slides and documentation
  • Easy for non-developers to read
  • Generated from the text source
  • Less likely to drift if re-rendered regularly
