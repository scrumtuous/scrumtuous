Concept 1

A Different View of the Same Design

A class diagram shows structure. A sequence diagram shows behavior for one scenario.

Class diagram

What classes exist?

What attributes and methods do they have?

How are they related?

Sequence diagram

Who starts the scenario?

What call happens next?

What does each object return?

MadShapes scenario
What happens when a student judges whether two displayed shapes have the same area? The class diagram tells us which objects exist. The sequence diagram tells us the order in which they interact.
Concept 2

Participants and Messages

A participant is one object involved in the scenario. Time moves downward. Each horizontal arrow is a message.

sequenceDiagram
participant S as Student
participant E as ExperimentController
participant C as ShapeComparator

S->>E: submitJudgement("SAME")
E->>C: sameArea(shapeA, shapeB)
C-->>E: true
E-->>S: "Correct"
Canvas example: participants, lifelines, calls, and returns
Read from top to bottom. Solid arrows are calls. Dashed arrows are returns.
Notation check: ->> is a synchronous call. -->> is the return.

🌸 Quick check

Which arrow is the return in Mermaid: ->> or -->>?

-->>

The dashed arrow represents the return message.
Concept 3

Synchronous Calls and Matching Returns

A synchronous call means the caller waits for the called object to finish. This is exactly what a normal Java method call does.

1️⃣ Caller sends a message controller->>circle: calcArea()
2️⃣ Called object works Circle calculates its area.
3️⃣ Return comes back circle-->>controller: 78.54 
sequenceDiagram
participant E as ExperimentController
participant C as Circle

E->>C: calcArea()
C-->>E: 78.54
Good diagram habit: show the return, even when it is just done or void. It makes the interaction easier to follow.
Concept 4

Activation Bars: Who Is Actually Doing Work?

The thin vertical rectangle on a lifeline shows when that participant is active.

sequenceDiagram
participant E as ExperimentController
participant C as ShapeComparator
participant A as Circle
participant B as Rectangle

E->>+C: sameArea(A, B)
C->>+A: calcArea()
A-->>-C: 78.54
C->>+B: calcArea()
B-->>-C: 80.00
C-->>-E: false
Canvas example: nested activation bars
The comparator stays active while it waits for each shape to return an area.
Design smell clue
A participant active for almost the entire diagram may be doing too much. Sequence diagrams can reveal responsibility problems that are harder to notice in a class diagram.
Later connection: this is another way to spot a central manager or orchestrator that has absorbed too much responsibility.
Concept 5

alt: Show a Real Conditional Path

Use an alt fragment when the workflow truly branches into different sequences of messages.

sequenceDiagram
participant S as Student
participant E as ExperimentController
participant C as ShapeComparator
participant R as ResultRecorder

S->>+E: submitJudgement("SAME")
E->>+C: sameArea(shapeA, shapeB)
C-->>-E: true

alt judgement is correct
    E->>+R: recordCorrect()
    R-->>-E: done
    E-->>S: "Correct"
else judgement is incorrect
    E->>+R: recordIncorrect()
    R-->>-E: done
    E-->>S: "Try again"
end
Canvas example: alt fragment
Each branch contains a different sequence of messages, not merely a note.
Direct exam connection: for "order valid" vs "order invalid", use an alt fragment with one branch for execution and another for rejection.

🔀 Your challenge

What is wrong with using a single straight-line sequence and adding a comment saying "sometimes rejected"?

A comment does not show the different behavior.
An alt fragment makes the valid and invalid message sequences explicit.
Concept 6

Do Not Turn Every Rule Into Its Own Branch

A sequence diagram should explain the scenario clearly, not reproduce every possible internal validation rule.

Too much

  • alt quantity negative
  • alt price invalid
  • alt risk limit exceeded
  • alt missing instrument
  • alt unsupported side

Enough for this lab

  • Validate the order
  • alt order is valid
  • else order is invalid
  • Show different message sequences
Reasoning over exhaustiveness: one valid/invalid alt branch is enough to demonstrate conditional workflow modeling for this lab.
ROFLGator says simplify If the diagram needs six nested validation fragments to explain one submission, it may be modeling implementation details instead of the workflow.
Read critically

A Sequence Diagram Is a Hypothesis About Behavior

1️⃣ Does the message order match the requirement?
2️⃣ Does one participant receive far more messages than everyone else?
3️⃣ Does every alt branch correspond to a real requirement?
4️⃣ Do calls have matching returns?
5️⃣ Are activation bars balanced and understandable?
6️⃣ Are all participants classes that actually exist in the class diagram?
Peer review preview: a sequence diagram can look polished and still model the wrong order of operations. Review the behavior, not just the appearance.
