Operation 1

Functions & Type Hints

A function gives a name to logic you want to reuse. Parameters are inputs; return sends a result back.

def passenger_fare_with_fee(
    fare: float,
    fee: float
) -> float:
    return fare + fee

total = passenger_fare_with_fee(7.25, 2.00)
print(total)
Read it like English: the function expects fare and fee to be floats, and the arrow says it intends to return a float.
QUIZ ALERT
Type hints are not normally enforced at runtime. fare: float and -> float document intent and help tools, but Python itself does not automatically reject every wrong type.

Operation 2

Default & Keyword Arguments

A default argument supplies a value when the caller leaves that argument out. A keyword argument names the parameter explicitly.

def classify_fare(
    fare: float,
    threshold: float = 50
) -> str:
    if fare > threshold:
        return "high"
    return "normal"

print(classify_fare(71.28))
print(classify_fare(71.28, threshold=100))

The first call uses the default 50. The second explicitly overrides it with 100.

QUIZ ALERT
Do not use a mutable object such as [] or {} as a default unless you deliberately want it shared. Default values are created once when the function is defined.

🚫 Risky

def add_note(name, notes=[]):
    notes.append(name)
    return notes

The same list can be reused across calls.

✅ Safer

def add_note(name, notes=None):
    if notes is None:
        notes = []
    notes.append(name)
    return notes

Each call gets a fresh list when no list is supplied.

Operation 3

Positional vs Keyword Calls

Positional arguments are matched by order. Keyword arguments are matched by parameter name.

Positional

fare_with_fee(7.25, 2.00)

Python matches 7.25 to the first parameter and 2.00 to the second.

Keyword

fare_with_fee(
    fare=7.25,
    fee=2.00
)

The names make the call easier to read.

Good habit: use keyword arguments when the meaning would be unclear from position alone.

Operation 4

Well-Behaved Modules

A Python file can be a reusable module. Docstrings explain its purpose, while the __main__ guard prevents demo code from running when the file is imported elsewhere.

"""titanic_math.py — passenger calculations."""

def fare_per_year(age, fare):
    """Return fare divided by passenger age."""
    return fare / age

if __name__ == "__main__":
    print(fare_per_year(22, 7.25))
QUIZ ALERT
if __name__ == "__main__": runs only when the file is executed directly. Importing the module does not run that block, which avoids surprise side effects.
Run file directly➡️__main__ block runs Import file➡️__main__ block skips

Operation 5

Custom Exceptions

Built-in exceptions describe Python-level problems. A custom exception can describe a problem in your own business or data domain.

class InvalidPassengerError(Exception):
    """Passenger data failed validation."""

def validate_fare(fare):
    if fare < 0:
        raise InvalidPassengerError(
            f"fare cannot be negative: {fare}"
        )
QUIZ ALERT
Custom exceptions are ideal for business-rule violations. Example: negative fare, impossible age, or invalid passenger class. They are different from a Python type error.

Operation 6

Multiple except Blocks

Different kinds of failures deserve different handling. Avoid a giant catch-all when you know what kinds of problems you expect.

try:
    age = float(passenger["age"])
    validate_age(age)

except (TypeError, ValueError) as e:
    print(f"Bad data type: {e}")

except InvalidAgeError as e:
    print(f"Rule violation: {e}")
QUIZ ALERT
Catch (TypeError, ValueError) together when they should be handled the same way. Keep a custom exception such as InvalidPassengerError separate when it represents a different kind of problem.
Big principle: narrow, specific exception handling is easier to debug and less likely to silently hide data-quality problems.

Operation 7

else and finally

else runs only if the try succeeds. finally always runs — whether the operation worked or failed.

try:
    fare = float(passenger["fare"])
    validate_fare(fare)

except (TypeError, ValueError):
    print("Bad fare")

except InvalidPassengerError as e:
    print(f"Skipped: {e}")

else:
    total += fare

finally:
    print("processed")
QUIZ ALERT
else is for success-only logic. finally is for logic that must happen no matter what. Do not put success-only work in finally.

✅ else

Add the fare to the total only if validation succeeded.

✅ finally

Print a status marker or perform unconditional cleanup.

Operation 8

Re-raising with Context

Sometimes you should not swallow an exception. Instead, add useful context and let the failure keep travelling upward.

def safe_fare(passenger: dict) -> float:
    try:
        fare = float(passenger["fare"])
        validate_fare(fare)
        return fare

    except InvalidPassengerError as e:
        raise InvalidPassengerError(
            f"{passenger['name']}: {e}"
        ) from e
QUIZ ALERT
raise ... from e preserves the original exception as the visible cause. That means you can add passenger context without hiding the root problem.
Negative fare➡️ InvalidPassengerError➡️ Add passenger name➡️ Re-raise with from e

Create a small program that: validates age and fare, catches (TypeError, ValueError) separately from your custom exception, adds fare to a total only in else, and always prints "processed" in finally.

class InvalidPassengerError(Exception):
    pass

def validate_fare(fare):
    if fare < 0:
        raise InvalidPassengerError(
            f"bad fare: {fare}"
        )

total = 0.0

for passenger in passengers:
    try:
        age = float(passenger["age"])
        fare = float(passenger["fare"])
        validate_fare(fare)

    except (TypeError, ValueError) as e:
        print(f"Bad data type: {e}")

    except InvalidPassengerError as e:
        print(f"Rule violation: {e}")

    else:
        total += fare

    finally:
        print("processed")
